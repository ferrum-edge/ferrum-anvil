# Protocol adapters: capabilities and limitations

Status as of this change. It covers the non-request/response adapters: WebSocket, gRPC, server-sent events (SSE), raw TCP/TLS and UDP/DTLS. It also covers the HTTP/3 policy cases in the failure matrix and TLS 1.3 / QUIC 0-RTT early data for HTTP requests (§3.12). HTTP/1.1 and HTTP/2 are documented with the HTTP adapter.

Support is not one yes/no per protocol (build plan §7). Each protocol is rated on four separate dimensions:

- **Interactive**: the desktop session API, `Engine::open_session`.
- **Automation**: collection/CLI execution, `Engine::execute`.
- **Load readiness**: what `anvil-load` measures with this adapter: its load unit, denominators and refusals (see [load.md](load.md#load-units-per-protocol-load-013)).
- **Diagnostic detail**: what the evidence and findings actually cover.

## 2. Shared behavior (all session protocols)

- **One preparation path.** `sessions.rs` reuses `http_exec::prepare_all`, so these behave exactly as for HTTP: variables, settings layers, the auth profile, TLS profile, trust, proxy selection, DNS overrides, IP preference and timeouts. Accepted schemes are `ws`/`wss`, `grpc`/`grpcs`/`http`/`https`, `http`/`https` for SSE, `tcp`/`tls` and `udp`/`dtls`.
- **Auth.** Auth is applied per send, as headers or query parameters, for WebSocket, gRPC and SSE. OAuth tokens come from the shared token cache. A few combinations fail before any traffic with `unsupported_combination`:
  - an auth profile that rewrites the body (WS-Security);
  - query-parameter auth on gRPC;
  - any auth profile on raw TCP/UDP, because payloads are sent verbatim. Client certificates come from the TLS profile instead. UDP through a MASQUE proxy is the exception: auth and the request's headers go on the CONNECT-UDP request to the proxy (§3.8).
  - JWT-SVID auth (§3.11) is fetched and checked before the session is prepared, for the protocols above; a failed check or an unreachable Workload API ends the session before any traffic, exactly as for HTTP.
- **Combinations refused before traffic** (`unsupported_combination`, `phase = prepare`, `dispatch = not_dispatched`):
  - a proxy with UDP/DTLS, except through an HBONE proxy (§3.9): HTTP CONNECT and SOCKS5 tunnels carry only TCP; an HBONE proxy carries UDP (and DTLS inside it) as a datagram tunnel, but not a PROXY protocol envelope; and no proxy carries the QUIC connection of UDP through a MASQUE proxy;
  - WebSocket over HTTP/3 with `ws://` (QUIC is always encrypted) or through a proxy;
  - native gRPC with the HTTP/1.1-only policy (gRPC-Web runs over HTTP/1.1), or `plaintext` with a TLS URL;
  - gRPC or gRPC-Web over HTTP/3 (both HTTP/3 policies) with a cleartext URL (QUIC is always encrypted) or through a proxy;
  - gRPC-Web with a client-streaming or bidirectional method, or with server reflection as the schema source (reflection is itself a bidirectional-streaming RPC); gRPC-Web with h2c and a TLS URL, or HTTP/2-only and a cleartext URL;
  - SSE with the forced HTTP/3 policy and an `http://` URL or a proxy (the automatic HTTP/3 policy records the refused HTTP/3 attempt and falls back to TCP instead);
  - a MASQUE proxy URL that is not `https://`, or not an origin; a URI Template without both `{target_host}` and `{target_port}`; a PROXY datagram envelope with a MASQUE tunnel (§3.8);
  - a gRPC call mode that does not match the method descriptor. Unary alone never proves streaming;
  - a request-level PROXY header (`proxy_protocol`) with HTTP/3 (either HTTP/3 policy, or WebSocket over HTTP/3), with any proxy (HTTP, HTTPS, SOCKS5 or HBONE), or on raw TCP or UDP, which have their own settings (§3.10).
- **Proxies.** TCP-based sessions go through the configured HTTP or SOCKS5 proxy as a CONNECT tunnel. This includes `ws://` and cleartext SSE. A mesh HBONE proxy works the same way (§3.9): WebSocket, raw TCP/TLS, SSE and gRPC run over the HTTP/2 CONNECT stream, and UDP runs over it as a datagram tunnel.
- **Transcripts.** Every message, event, frame or datagram becomes a `StreamMessage` and is also emitted live as `ExecutionEvent::Message`. The transcript is bounded:
  - The defaults are 2,000 entries and a 2 KiB preview per entry.
  - It keeps the first half and the most recent half. Entries in between are counted in `dropped_messages`.
  - `sent_count`/`received_count` and the byte totals always cover the whole session. The `MessageCount` assertion uses `received_count`.
  - Previews and event ids pass through the engine's `Redactor`, as do WebSocket close reasons and `grpc-message`. That redactor scrubs the exact secret values used in the run, so no transcript or live event contains a resolved secret. A test covers this for WSS with bearer auth.
  - Binary previews are hex.
- **Outcome derivation.** The adapters return a `ProtocolStatus` override and a transcript to `record::assemble`. When a session actually opened, transport completion comes from how the session ended, not from HTTP body framing:
  - no failure → `completed`;
  - user cancel → `canceled`;
  - any other failure → `incomplete`. Examples: an abnormal close, a mid-stream reset, or a gRPC deadline with no status.

  gRPC with a missing terminal status is always `incomplete`, and its application state is never success. Application state comes from the protocol status: gRPC codes, WebSocket close codes and the SSE HTTP status.
- **Interactive API.** `Engine::open_session(ctx, events)` prepares the session immediately. If preparation fails, the returned handle finishes at once with a local-failure record. Otherwise the session runs in a task:
  - `SessionHandle::send(SessionCommand)` rejects commands a protocol cannot express, such as WebSocket `HalfClose` or TCP `Ping`, with `SessionError::Unsupported` instead of dropping them silently.
  - `close()` is a graceful close. `cancel()` aborts.
  - `finish()` waits for the end and returns the full `ExecutionOutput`. It does not close the session, so call `close()` or `cancel()` first unless the peer is expected to end it.
  - Interactive sessions ignore the total deadline and the automation idle-close.
  - Dropping every command sender also ends the session gracefully.
- **0-RTT early data** (§3.12) applies to HTTP requests only. When a settings layer enables it, sessions (WebSocket, gRPC, SSE, TCP, UDP) keep full handshakes, and the effective request says so in its "added by Anvil" notes.
- **Engine-derived findings.** The generic rules have no finding for a few adapter observations. For these, the engine adds findings with inline wording: `grpc.reflection_unavailable`, `udp.icmp_port_unreachable` and `udp.repeated_payloads`. It also adds `grpc_web.no_trailer_frame` and `grpc.framing_invalid`, whose wording is in the diagnostics catalog. Each one states what it does not prove.

## 3. Per-protocol details

### 3.1 WebSocket

- **Libraries.** hyper 1.x does the bootstrap for HTTP/1.1 and HTTP/2, and `hyper::upgrade::on` hands over the stream. For HTTP/3, quinn + `h3` carry the extended CONNECT, and the request stream's DATA frames are bridged to a byte stream. tokio-tungstenite 0.30 runs the frames in all three cases, with the same session code. tungstenite 0.30 is vendored with a small permessage-deflate codec (`vendor/README.md`).
- **Bootstrap request.** For HTTP/1.1, Anvil generates `Sec-WebSocket-Key` and verifies the accept key. Over TLS, HTTP/1.1 offers ALPN `http/1.1` only. User headers win over the handshake defaults, which allows deliberately malformed handshake tests.
- **Subprotocols.** They are offered in order. If the server selects one that was not offered, that is a `ws_protocol_error`. If the server selects none, that is recorded as a note.
- **Message limit.** `max_message_bytes` is a local inbound ceiling on both messages and frames. Outbound size is not limited. When an inbound message goes over the limit, Anvil closes with **1009**, sets `closed_by = client` and records a `ws_message_too_large` failure. When the peer's limit triggers the 1009, it is recorded with `closed_by = peer` and no transport failure. `ws.closed_too_big` keeps both explanations as alternatives.
- **Abnormal ends.** A connection that ends without a Close frame is reported as `close_code = 1006` with `closed_by = abnormal` and a `body_incomplete`/`body_reset` failure. 1006 is a local designation, not a code the peer sent (RFC 6455 §7.1.5).
- **Teardown after Close.** Once the peer's Close frame has arrived, the way TCP/TLS is torn down does not change the outcome. That covers an RST, or a missing TLS `close_notify`.
- **Rejected handshakes.** A non-101 answer (non-200 for HTTP/2) keeps the HTTP response as evidence (status, headers, bounded body) with a `ws_handshake_rejected` failure. The HTTP status findings still apply.
- **RFC 9220 (WebSocket over HTTP/3).**
  - **Library.** `h3` 0.0.8 models `:protocol` as a closed type that cannot express `websocket`. Upstream fixed this in hyperium/h3#236 (`Protocol::WEBSOCKET`), which no release contains yet. The workspace vendors `h3` 0.0.8 with exactly that commit applied (`vendor/README.md`), the same approach Ferrum Edge 0.9.5 uses.
  - **Settings first.** RFC 9220 §3 forbids sending `:protocol` until the server's SETTINGS enable extended CONNECT. Anvil waits for the SETTINGS frame (up to the response-header timeout, at most 5 s). If they do not enable it, or none arrive, it fails with `ws_handshake_rejected` in the `protocol_handshake` phase and sends nothing.
  - **Refused before traffic.** `ws://` (QUIC is always encrypted) and any proxy give `unsupported_combination`. There is never a fallback to HTTP/1.1 or HTTP/2: a UDP-blocked path is a `quic_handshake_timeout`.
  - **Evidence.** The connection record is the HTTP/3 one: DNS, QUIC handshake (TLS 1.3 inside) and HTTP/3 setup, with connect `not_applicable`. The session's byte counters are the WebSocket bytes carried in the stream's DATA frames, not QUIC packet bytes. A stream error that ends the session is appended to the failure message.
  - **Live.** PROTO-013 passes against Ferrum Edge 0.9.5 and 0.9.7 (`docs/lab/streams-cpdp.md`), which bridges the session to the backend as an HTTP/1.1 Upgrade.
- **permessage-deflate (RFC 7692).** The same for all three bootstraps.
  - **Off by default, opt-in per request** (`websocket.permessage_deflate.enabled`; the desktop WebSocket editor's Compression section). Browsers, Python `websockets` and Node `ws` clients offer it by default; Anvil does not, so a saved request (including every request saved before this existed) keeps the uncompressed wire it had, and a diagnostic run is not silently changed into a compressed one. The offer's parameters are `server_no_context_takeover`, `client_no_context_takeover`, `server_max_window_bits` (8–15) and `client_max_window_bits`, which is offered without a value (as browsers do: the server may limit Anvil's window) or with a value 8–15. Values outside 8–15, or the toggle together with a user `Sec-WebSocket-Extensions` header, are refused before traffic (`unsupported_combination`). With the toggle off, a user header is sent verbatim, but Anvil runs no codec for it.
  - **The answer is validated** (RFC 6455 §4.1, RFC 7692 §7). A handshake whose `Sec-WebSocket-Extensions` answer names an extension that was not offered (also when nothing was offered), names permessage-deflate twice, repeats a parameter, carries an unknown parameter, a value on `*_no_context_takeover`, a window outside 8–15 or with a leading zero, a window larger than the one offered, or drops `server_no_context_takeover` / `server_max_window_bits` that the offer asked for, fails in `protocol_handshake` with `ws_protocol_error`, the typed reason in the message and in the evidence (`negotiation = rejected`, `problem`), and finding `ws.extension_answer_refused`. No message is exchanged.
  - **Offered, not negotiated** (an answer without the extension) is information, not an error: `ws.deflate_not_negotiated` (info, scope unknown), and the session runs uncompressed. Any server may decline, and a proxy or gateway may strip the offer; the finding names no hop.
  - **Codec.** Outgoing text and binary messages are compressed with a sync flush and the `0x00 0x00 0xff 0xff` tail removed; an empty message is the single `0x00` octet. Control frames are never compressed. Incoming compressed messages (RSV1 on the first frame) are inflated fragment by fragment with the tail appended after the last one; a zero-length compressed message is empty and does not disturb the shared window. Context takeover follows the agreement in each direction (Anvil also keeps its own offered `client_no_context_takeover` and window when the answer is silent about them). The compressor uses the agreed Anvil window; the decompressor keeps a 2^15 window, so it decodes any server window. An agreed Anvil window of 2^8, which zlib cannot produce, makes Anvil send its messages uncompressed (RSV1 clear), which RFC 7692 §6 allows; the evidence and a note say so.
  - **Limits.** `max_message_bytes` limits the **decompressed** message; inflation stops as soon as it is passed (decompression-bomb protection). Anvil then closes with 1009, `closed_by = client`, `ws_message_too_large` whose message says the limit was reached after decompression, the violation `too_large_after_decompression` (limit and compressed bytes received), and finding `ws.too_large_after_decompression` instead of the generic `ws.closed_too_big`. The frame limit stays on the wire size. A 1009 from the peer is still `closed_by = peer` with `ws.closed_too_big`.
  - **Peer violations.** A data message with RSV1 although nothing was negotiated (whether or not Anvil offered) is `ws.compressed_without_negotiation`; a compressed message that does not inflate is `ws.decompression_failed`. Both close with 1002 and a `ws_protocol_error` attributed to the peer (scope `response_delivery`), with the violation in the evidence. RSV1 on a control or continuation frame stays a generic protocol violation.
  - **Evidence.** `ProtocolStatus::WebSocket.extensions`: the offer, the verbatim (bounded, redacted) answer, the negotiation state, the agreed parameters, per-direction totals (messages, compressed messages, uncompressed payload bytes, data-frame payload bytes on the wire, counted from frame headers as they cross the stream) and any violation. It is absent when nothing was offered or answered. The prepared request lists the offer; the inspector notes and a transcript note state the outcome. Previews show the decompressed payload, redacted as usual. The CLI prints the same evidence.
  - **Through Ferrum Edge 0.9.5 and 0.9.7:** the gateway never negotiates it. It strips the client's offer before the backend handshake and never forwards an answer (`src/proxy/mod.rs` `is_websocket_backend_strip_header` and `WEBSOCKET_TRANSPORT_MANAGED_RESPONSE_HEADERS` for HTTP/1.1 and HTTP/2, `src/http3/websocket.rs` for HTTP/3), so Anvil records "offered, not negotiated" and the session runs uncompressed. Live in the streams lab (WS-DEFLATE-001/002/003, WS-DEFLATE-lookalike; `docs/lab/streams-cpdp.md`).
- **Not implemented.** Extensions other than permessage-deflate, fragmented-send controls, and automatic reconnect.

### 3.2 gRPC

- **Wire formats.** `GrpcSpec.wire` selects native gRPC (`grpc`, the default: records saved before the field existed load as native), gRPC-Web binary (`grpc_web`, `application/grpc-web+proto`) or gRPC-Web text (`grpc_web_text`, `application/grpc-web-text`). The HTTP version comes from the request's HTTP version policy:

  | Policy | Native gRPC | gRPC-Web |
  |---|---|---|
  | Auto | HTTP/2: ALPN `h2` over TLS, h2c in cleartext | ALPN `h2`, `http/1.1` over TLS (the negotiated one is used); HTTP/1.1 in cleartext |
  | HTTP/1.1 only | refused | HTTP/1.1 (ALPN `http/1.1` over TLS) |
  | HTTP/2 only | HTTP/2 (as Auto) | ALPN `h2` only over TLS (a mismatch is `tls_alpn_mismatch`); refused for a cleartext URL |
  | h2c | h2c | h2c; refused for a TLS URL |
  | HTTP/3 only | HTTP/3 over QUIC | HTTP/3 over QUIC |
  | HTTP/3 with fallback | HTTP/3, then HTTP/2 as a separate attempt | HTTP/3, then the Auto TCP choice as a separate attempt |

  HTTP/3 needs a TLS URL and no proxy (refused before traffic otherwise).
- **Transport (native).**
  - TLS with ALPN `h2` is required over TCP. Negotiating anything else is a `tls_alpn_mismatch`.
  - Cleartext targets (`grpc://`, `http://`) use h2c with prior knowledge.
  - An optional URL path prefix goes in front of `/<service>/<method>`, for gateway routing.
- **gRPC over HTTP/3.** Each call opens a fresh QUIC connection with the shared `quic_connect` (DNS, then the QUIC handshake with TLS 1.3 inside and ALPN `h3`, then HTTP/3 setup; the connect phase is `not_applicable` and there is no TCP-TLS phase). The call is a `POST` request stream: its HEADERS carry the same fields as over HTTP/2, request DATA frames carry the length-prefixed messages (the stream's send side is finished for the half-close), and the status is read from the HTTP/3 trailers or the headers of a trailers-only answer. Both directions run concurrently, so bidirectional and interactive client-streaming calls work as over HTTP/2. A deadline, cancel or local failure resets the stream with `H3_REQUEST_CANCELLED`; the connection is then closed with `H3_NO_ERROR`. The response half is stopped with that code even while a read is waiting for data, which needs a vendored `h3-quinn` 0.0.10 with a patch (it panicked there; `vendor/README.md`). The attempt's byte counters are the request stream's DATA bytes, not QUIC packet bytes. Server reflection runs on the call's own QUIC connection.
  - **Forced HTTP/3** never uses TCP: a UDP-blocked path is a `quic_handshake_timeout` with nothing dispatched.
  - **HTTP/3 with fallback** falls back only when the HTTP/3 attempt failed **before the call was sent** (dispatch `not_dispatched`, no response, not a cancel or a local refusal). The second attempt has reason `protocol_fallback{from: h3}`, and the record carries `client.h3.fallback_used` and the `protocol_fallback` warning. A call that may have reached the server over HTTP/3 is never repeated, because an RPC is not assumed to be idempotent.
- **gRPC-Web** (PROTOCOL-WEB).
  - **Request.** `POST` with `content-type` and `accept` set to the wire's media type, `x-grpc-web: 1`, `grpc-timeout` from the deadline, the metadata and the auth headers. There is no `te: trailers`. The body is the single length-prefixed message, base64-encoded in text mode; its length is known, so HTTP/1.1 sends `Content-Length`. The prepared body (and what an auth profile signs) is exactly those bytes.
  - **Only unary and server streaming.** A gRPC-Web client sends the whole request body before it reads the response, so there is no client stream and no half-close. Client-streaming and bidirectional calls are refused before traffic (`unsupported_combination`, field `grpc.wire`), and so is server reflection (field `grpc.schema`), because the reflection service is itself bidirectional. Load a `.proto` or a descriptor set instead.
  - **Response framing.** The body mode follows the response `content-type` (`application/grpc-web-text*` is base64; any other `application/grpc*` type is binary; a missing type falls back to the request's mode). Text bodies are decoded incrementally, 4 characters at a time, so a server that base64-encodes each flush separately (with `=` padding in the middle of the body) is handled, and at most three characters are held between chunks. Frames are `0x00`/`0x01` messages and one `0x80` trailer frame whose payload is a `name: value` header block (bounded to 1 MiB and 1,024 entries). `0x81` is refused as undefined.
  - **Status source**, reported separately from the HTTP status: `trailer_frame` (the trailer frame's `grpc-status`), `trailers_only` (the status in the response headers, empty body), `trailers` (the status arrived in HTTP trailers instead of a trailer frame: recorded, with a note that browser gRPC-Web clients cannot read HTTP trailers, and a `grpc_web.no_trailer_frame` warning), or `missing`. A body that ends cleanly without a trailer frame and without a trailers-only status is **missing**: transport `incomplete`, application never success, and `grpc_web.no_trailer_frame` (error) next to `app.grpc_status_missing`. Neither finding claims whether any gateway translated gRPC-Web.
  - **Invalid framing.** Data after the trailer frame (including a second, appended trailer frame), an invalid flag, a malformed trailer block or invalid base64 stops parsing, but the HTTP body is still read to its end so its completeness is reported as observed. The failure is `http_protocol_error` and the finding is `grpc.framing_invalid` (instead of a misleading "body did not finish"). A status read before the problem is kept, but the call is not a complete success. A truncated frame or a base64 quantum cut off at the end remains `body_incomplete`.
  - Native gRPC gets the same framing checks: a `0x80` frame in a native stream is invalid framing (it was previously misreported as a local size limit), and a response whose content type is not `application/grpc*` (for example an HTML error page) is kept as evidence instead of being parsed as frames.
- **Request headers (native).** `content-type: application/grpc`, `te: trailers`, `user-agent: grpc-anvil/<version>`, the metadata entries, and the auth headers. `grpc-*` metadata keys are refused. `grpc-timeout` is sent from `deadline_ms`.
- **Deadline.** The deadline is also enforced locally. When it elapses the stream is reset, the failure is `total_timeout` with `deadline_ms`, and the status is recorded as **missing**. Anvil does not invent a `DEADLINE_EXCEEDED`.
- **Status.** It comes from the trailers, the trailer frame (gRPC-Web), or the headers of a trailers-only response, and is labeled with its source. `grpc-status-details-bin` is decoded as `google.rpc.Status` (code, message and detail type URLs), and the summary goes into the prepared inferred notes.
- **Schemas.**
  - `.proto` sources are compiled in-process by `protox`. Imports resolve only among the provided files, by attachment file name, plus the bundled Google well-known types. Nothing is read from disk.
  - A serialized `FileDescriptorSet` is also accepted.
  - The third source is server reflection (native gRPC only). v1 is tried first; if it is UNIMPLEMENTED, v1alpha is tried. The dependency closure is fetched with `file_by_filename`, capped at 64 requests. Reflection runs on the same HTTP/2 or HTTP/3 connection as the call.
  - A refused reflection (PROTO-017) produces `grpc.reflection_unavailable`. The method is not called, dispatch is `not_dispatched`, and there is no `app.grpc_status` finding about the service.
- **JSON mapping.** `prost-reflect` handles JSON ↔ DynamicMessage using proto3 JSON mapping. Received messages are shown as JSON with default serialization options.
- **Compression.** Inbound `grpc-encoding: gzip` messages are decompressed up to the per-message limit. Anvil never compresses outbound messages and does not advertise `grpc-accept-encoding`.
- **Receive limit.** The default is 64 MiB per message, and it is also capped by `limits.max_response_bytes`.
- **Live.** Against Ferrum Edge v0.9.7 (`docs/lab/streams-cpdp.md`): gRPC over HTTP/3 in all four call modes through the QUIC listener, which bridges to an h2c backend; forced HTTP/3 on a UDP-blocked path; HTTP/3-with-fallback; and gRPC-Web binary and text through the `grpc_web` plugin over HTTP/1.1, HTTP/2 and HTTP/3. On a route **without** the plugin, v0.9.7 passes gRPC-Web through untranslated but, over HTTP/1.1 and HTTP/2, appends its own synthesized `grpc-status: 2` trailer frame after the backend's trailer frame; Anvil reports that as `grpc.framing_invalid`, not as a success.
- **Not implemented.** Retries, hedging and service config; load-balancing policies; outbound compression; keepalive pings as a session command (HTTP/2 and QUIC PINGs are connection-level); gRPC-Web request trailer frames (Anvil sends none); gRPC-Web `+json` or other message-format suffixes (only protobuf); connection reuse across manually sent gRPC calls (the load engine reuses pooled channels per virtual user in its persistent mode, see [load.md](load.md#load-units-per-protocol-load-013)).
- **Proto import names** must match the stored attachment file names. A project that imports `foo/bar.proto` must store the file under that name.

### 3.3 Server-sent events

- **Parsing.** Incremental parsing per the HTML Standard's event-stream rules: `id`, `event`, `data` (multi-line), `retry`, comments, CR/LF/CRLF split across chunks, and a leading BOM. An `id` that contains NUL is ignored. A single line is capped at 1 MiB, or `max_response_bytes` if that is lower.
- **Request headers.** `Accept: text/event-stream` and `Cache-Control: no-cache`. `Accept-Encoding: identity` is sent unless the user set it, because events are parsed as they arrive and are not decompressed. `Last-Event-ID` is sent when configured.
- **Stop conditions.** `max_events` gives `closed_by = client` and a transport of `completed`. An idle period with no bytes at all gives `closed_by = timeout` (keep-alive comments count as activity). Explicit cancel gives `closed_by = client` and a transport of `canceled`, and the `sse.canceled` finding says this is not a server timeout. The server ending the stream gives `closed_by = peer`.
- **Reconnect.** It is off by default and happens only when enabled. It triggers only after an **abnormal** end, such as a reset or a truncated chunked body, and is limited to 5 attempts.
  - It honors the server's `retry:` delay (default 1 s, capped at 30 s) and sends `Last-Event-ID`.
  - Partial event data from the broken stream is discarded.
  - Each reconnection is its own attempt, with reason `retry{after: <kind>}`.
  - A clean end of stream is recorded as the server closing and is **not** reconnected. That is a deliberate difference from browser `EventSource`.
- **HTTP/3.** With `http3_only` or `http3_with_fallback`, an `https://` stream runs over QUIC: `quic_connect` measures DNS and the QUIC handshake (TLS 1.3 inside; connect is `not_applicable`), the request is sent on an HTTP/3 request stream, and the event stream is parsed from the stream's DATA frames as they arrive, with every semantic above unchanged.
  - A reset stream (for example `H3_INTERNAL_ERROR` from a gateway whose backend aborted) is a `body_reset` in the `session` phase with the peer's HTTP/3 error code in `quic_error_code`. Transport is `incomplete` and `closed_by = abnormal`, never success.
  - Every attempt, including each reconnection, uses a new QUIC connection.
  - Forced HTTP/3 never touches TCP. With `http3_with_fallback`, an HTTP/3 attempt that produced no response is recorded and followed by a separate TCP attempt with reason `protocol_fallback{from: h3}`, and `client.h3.fallback_used` is reported.
  - The connection byte counters are QUIC UDP payload bytes. Anvil ends an HTTP/3 stream by closing its QUIC connection with `H3_NO_ERROR`, which also ends the request stream.
  - Live against Ferrum Edge 0.9.7 in the `h3x` lab (`docs/lab/h3x.md`).
- **Not implemented.** Decompression of compressed event streams.

### 3.4 Raw TCP / TLS

- **Connection setup.** Uses the shared connector: DNS, TCP, proxy tunnel (HTTP CONNECT or SOCKS5), then TLS with the profile's trust and client identity. TLS evidence matches HTTPS, including the client-certificate request and what was presented. No ALPN is offered.
- **Payloads.** Text (UTF-8, verbatim), hex (whitespace, `:` and `0x` allowed) or base64. Variables are resolved first.
- **Framing presets.** None, newline-delimited (`\r\n` accepted on receive), or a big-endian u16 or u32 length prefix. A payload the preset cannot represent fails locally with `body_serialization`, for example more than 65,535 bytes with a u16 prefix. Incoming frames above the read limit stop with `response_too_large_local`. Without a preset, each read is recorded as a chunk and `expect_frames` is ignored with a note, because TCP has no message boundaries.
- **Half-close.** `shutdown(Write)`, with a TLS `close_notify` first, keeps the read side open. A reply that arrives afterwards is preserved and gets the `tcp.reply_after_half_close` finding.
- **Stop conditions.** `expect_frames`, `max_read_bytes`, `read_idle_ms` (`closed_by = timeout`), the peer's FIN (`closed_by = peer`), a reset (`closed_by = abnormal` plus a `body_reset` failure), the total deadline, or cancel.
- **PROXY protocol.** An optional v1/v2 header written before any TLS; see §3.10.
- **Not implemented.** Application codecs (only arbitrary bytes are supported) and Unix sockets.

### 3.5 UDP

- **Socket.** The socket is bound to an ephemeral local port and `connect`ed to the destination. Only datagrams from that address are accepted, and the OS can report ICMP errors to it. There is no connect phase; it is marked not applicable.
- **Evidence.** Sent datagrams are recorded one per entry. The response window starts after the last send, or after each interactive send. Received datagrams are counted until `max_datagrams`.
- **Silence** is `udp.no_response`: "no response observed". It never claims delivery or an outage. Dispatch is `may_have_been_sent`, because UDP gives no acknowledgement.
- **ICMP port unreachable.** When the OS reports it, it is recorded as `udp.icmp_port_unreachable` with confidence **likely**. It is stronger than silence, but a firewall can generate it.
- **Loss and duplication.** Fewer responses than sends is `udp.partial_responses`. Payloads byte-identical to an earlier received payload are counted in `udp.repeated_payloads`, which is an observation and not a claim of duplicate delivery. Sequence-level loss or reorder accounting is not attempted, because UDP has no sequence numbers unless the application adds them.
- **Through a proxy.** Only an HBONE proxy profile (a datagram tunnel, §3.9) or a MASQUE proxy (§3.8) carries UDP. The proxy owns the socket toward the destination, so an ICMP error reaches it, never Anvil; silence stays "no response observed".
- **Not implemented.** Unconnected mode (replies from another address or port, as in TFTP), multicast or broadcast, and datagrams larger than 65,535 bytes.

### 3.6 DTLS

- **Implementation.** `dimpl` 0.6 with its RustCrypto provider, a dedicated DTLS implementation that is separate from the TLS adapter. The client sends a hybrid ClientHello that offers DTLS 1.2 and 1.3, and the negotiated version is recorded (`DTLSv1_2` / `DTLSv1_3`). Retransmissions follow dimpl's timers. The handshake deadline is the TLS-handshake timeout class, and when it expires the result is `dtls_handshake_timeout` with `deadline_ms`.
- **Certificate verification.**
  - dimpl verifies handshake signatures but does no PKI validation.
  - Anvil validates the peer's leaf itself, with the same webpki verifier the TLS profile builds for TLS: trust anchors, validity and name. It does this before releasing its next flight.
  - A failure aborts the handshake, typed as TLS verification (`tls_untrusted_issuer`, `tls_name_mismatch`, and so on) in the `dtls_handshake` phase. The presented certificate is kept as evidence and no application data is sent.
  - `verify = false` keeps encryption and records `bypassed{would_have_failed}`.
- **Client identity.** Taken from the TLS profile, with the same host bindings as TLS. It must be ECDSA P-256 or P-384. RSA and other keys fail locally with `client_identity_invalid`.
- **Peer rejection.** A fatal alert from the peer, such as an `unknown_ca` rejection of the client identity, is typed as `dtls_handshake_failed` with `tls_alert` set to the alert name. Our own verification result is kept separately, so the evidence shows which side rejected.
- **CertificateRequest.** Seen from the peer's plaintext flight for DTLS 1.2. It is reported as not observed (`None`) for DTLS 1.3, where that message is encrypted.
- **Library limits, stated plainly.**
  - dimpl exposes only the peer's **leaf** certificate. A server chain that needs an intermediate validates only if that intermediate is itself a configured trust anchor.
  - dimpl sends a **single** client certificate, never a chain. When the chain has more certificates, a note says so.
  - dimpl always needs a key pair. If the server asks for a client certificate and no identity is configured, an ephemeral self-signed certificate (`CN=anvil-ephemeral-dtls-client`) is what the server sees, and the evidence and notes say so.
  - The negotiated cipher suite is not exposed.
  - There is no session resumption, PSK mode, SRTP keying or connection ID.
- **Alert codes.** dimpl reports received alerts only in its formatted error text (`description=N`). The adapter reads the numeric code from that fixed format and infers nothing else from the text.
- **Datagram channel.** The handshake and the session run over a `DatagramChannel` (`anvil-transport/src/datagram.rs`): send one datagram, receive the next, and the largest datagram the path carries. Three channels exist: a UDP socket connected to the destination (optionally with a PROXY v2 envelope on every datagram, §3.10); an open RFC 9298 CONNECT-UDP tunnel (§3.8), where every DTLS record is one HTTP Datagram; and an open Ferrum Mesh HBONE datagram tunnel (§3.9, `HboneChannel` in `anvil-transport/src/hbone_udp.rs`), where every DTLS record is one `[u16 length][payload]` record on the HTTP/2 `CONNECT` stream. When the path carries less than dimpl's 1,150-byte default (QUIC DATAGRAM frames), records are sized to fit; an HBONE record carries up to 65,535 bytes, so records keep dimpl's default size there (the endpoint relays each record as one UDP datagram to the target, so the size that matters is the path beyond it). The channel moves datagrams only; each channel's own evidence (socket addresses, envelope, tunnel) is added by whoever opened it.
- **Through a tunnel.** `connection.tls` stays the DTLS evidence about the target (so verification and alert findings name the target) and `connection.tunnel` holds the proxy or endpoint leg. With MASQUE, a tunnel that never opens leaves the attempt as the CONNECT to the proxy; once it opens the attempt becomes the DTLS session (§3.8). With HBONE the attempt addresses the DTLS target throughout, as UDP through HBONE does, and a tunnel that never opens is exactly the UDP-through-HBONE record (§3.9). Either way a tunnel that never opens attempts no DTLS.

### 3.7 HTTP/3 policy (PROTO-006/007/008)

The HTTP/3 transport already existed. This change adds an HTTP/3 fixture server (quinn + h3) and the tests:

- **PROTO-006, forced success.** The record shows `protocol = h3`, ALPN `h3`, a completed `quic_handshake` phase, and connect `not_applicable`. There is no TCP or TLS-over-TCP phase.
- **PROTO-007, no UDP listener.** The result is `quic_handshake_timeout`, with a single attempt, and the TCP fixture on the same port sees no connection.
- **PROTO-008, automatic fallback.** Two attempts are recorded, the second with reason `protocol_fallback{from: h3}`. The response is not HTTP/3, and there is a `client.h3.fallback_used` finding plus a `protocol_fallback` warning. The fallback finding previously never fired, because the engine did not pass `protocol_fallback_from`. That is fixed.
- **0-RTT.** With the early-data opt-in, a new HTTP/3 connection resumes a session ticket and can carry the request as QUIC 0-RTT data (§3.12).
- **Pooled QUIC connections are bounded.** With connection reuse on, HTTP/3 requests share one pooled QUIC connection per pool key (isolation, destination and TLS profile). Each engine keeps at most 64 idle ones in total; one more closes the connection idle longest. The cap is per pool: the HTTP/1.1 and HTTP/2 pool has its own 64, so an engine holds at most 128 idle connections in all. QUIC keep-alives would hold an idle connection open indefinitely, so a background sweep closes connections idle for 90 s even when their destination is never used again, and stops while the pool is empty. The connection kept for a `425 Too Early` retry is closed after 10 s if the retry does not use it. A connection counts as idle only with no request in flight, so neither expiry, eviction nor clearing cuts a request short: a connection the pool gives up while it carries a request (or one never pooled, with connection reuse off) is closed when its last request ends. Anvil closes each connection explicitly with `H3_NO_ERROR`.

### 3.8 UDP through an HTTP/3 MASQUE proxy (RFC 9298 CONNECT-UDP)

- **Setting.** `udp.masque = { proxy_url, uri_template, datagrams }` on a UDP request. The request URL stays the UDP target (`udp://host:port`). `proxy_url` is the proxy's `https://host:port` origin and `uri_template` its RFC 9298 §2 URI Template path, default `/.well-known/masque/udp/{target_host}/{target_port}/`. `{target_host}` and `{target_port}` use RFC 6570 simple expansion (IPv6 colons become `%3A`); form-style `{?…}`/`{&…}` expansion is accepted too.
- **Why a UDP option and not a proxy profile.**
  - A MASQUE proxy is addressed by a URI Template, not a `host:port`, and it carries only UDP.
  - Proxy profiles are `host:port` HTTP/SOCKS tunnels inherited through settings layers by every protocol. A UDP-only kind would have to be refused for every HTTP, WebSocket, gRPC, SSE and TCP request that inherited it, and would still need a template.
  - The proxy's SETTINGS, answer and datagram encoding are evidence about this one exchange, and the target stays in the URL, where the rest of the UDP evidence refers to it.
  - Templates can use variables, so one proxy definition is still reusable across requests.
- **Bootstrap.** A fresh QUIC connection to the proxy, on which Anvil advertises `SETTINGS_H3_DATAGRAM`. Nothing is sent on a request stream until the proxy's SETTINGS arrive (up to the response-header timeout, at most 5 s) and enable extended CONNECT. Then Anvil sends `:method = CONNECT`, `:protocol = connect-udp`, `:scheme = https`, `:authority` = the proxy, `:path` = the expanded template and `capsule-protocol: ?1`, plus the request's own headers, a User-Agent and the auth headers (none of the HTTP body defaults).
- **Datagrams.** UDP payloads are HTTP Datagrams with Context ID 0.
  - `datagrams = auto` (default) uses QUIC DATAGRAM frames (quarter stream ID, context ID, payload) when the proxy's SETTINGS enable `SETTINGS_H3_DATAGRAM` and QUIC negotiated DATAGRAM frames. Otherwise it uses RFC 9297 DATAGRAM capsules on the CONNECT stream (§3.5).
  - `quic_datagrams` requires frames and fails before the request without them. `capsules` always uses capsules.
  - Both encodings are accepted on receive. Unknown capsule types are skipped without buffering their value; unregistered context IDs are dropped and counted.
  - The framing is implemented directly on quinn datagrams. The `h3-datagram` crate is not needed and the vendored h3 is unchanged.
- **Ferrum Edge.** The gateway's profile (its docs/http3.md, "CONNECT-UDP over HTTP/3") never negotiates `SETTINGS_H3_DATAGRAM` and carries HTTP Datagrams as DATAGRAM capsules. So `auto` uses capsules, and `quic_datagrams` fails before traffic with `masque.no_datagram_support`.
- **Evidence.**
  - The attempt is the CONNECT (method `CONNECT`, the proxy URL): DNS and QUIC phases to the proxy, a `protocol_handshake` detail naming the SETTINGS and the chosen encoding, and the proxy's status and headers.
  - The transcript, counts, window, repeated-payload count and dispatch rules are the direct UDP adapter's.
  - `ProtocolStatus::Udp.masque` records the proxy, target, SETTINGS (`extended_connect`, `h3_datagrams`), `connect_status`, the encoding, datagrams sent and received per encoding, dropped datagrams and the tunnel's `closed_by`.
  - TLS, trust and the Ferrum integration profile follow the proxy, the only HTTP peer.
- **Outcomes and findings.**
  - SETTINGS without extended CONNECT: `masque_unsupported` and `masque.extended_connect_unavailable` (confirmed). No SETTINGS in time: `masque.settings_not_received` (unknown). QUIC datagrams required but not offered: `masque.no_datagram_support`. Nothing is sent in any of these.
  - A non-2xx answer: `masque_refused` with the status, the (bounded) body kept, no datagram sent (`not_dispatched`), application `failure`, and `masque.proxy_refused` (confirmed; `Proxy-Status` and a JSON `error` are evidence) next to the generic HTTP status finding. Its explanation and "does not prove" say the refusal is the proxy's answer and not evidence that the target is down.
  - An open tunnel: silence is `udp.no_response`, exactly as for direct UDP. Anvil ends the tunnel after the window (FIN on the stream, `closed_by = client`). A proxy FIN is `closed_by = peer`.
  - A stream reset, a lost QUIC connection or a FIN inside a capsule is `closed_by = abnormal` with a typed failure (the peer's HTTP/3 code kept), transport `incomplete`, and `masque.tunnel_ended_abnormally`.
  - Every `masque.*` finding has scope `forward_proxy` and names the target only in "does not prove".
- **DTLS inside the tunnel** (`dtls://host:port` with `udp.masque`).
  - The tunnel opens exactly as for UDP. Then the DTLS client (§3.6) runs over the open tunnel: every DTLS record (handshake flights, retransmissions, application data, `close_notify`) is one HTTP Datagram with Context ID 0, in the tunnel's encoding. The proxy relays records verbatim; the DTLS session is end to end with the target.
  - The TLS profile applies to both legs: its trust and client identity to the QUIC handshake with the proxy, and to the DTLS handshake with the target (identities presented where the profile's host bindings allow). The request's headers and auth go on the CONNECT, as for UDP.
  - **A tunnel that never opens** (QUIC or SETTINGS failure, a missing capability, a refusal) is reported exactly as for UDP: the attempt is the CONNECT to the proxy, the refusal body is kept, `masque.*` findings apply, and no DTLS was attempted (no `dtls_handshake` phase, no DTLS evidence).
  - **An open tunnel** changes the attempt into the DTLS session with the target (method `DTLS`, the `dtls://` URL): its phases are DNS and connect `not_applicable` (the proxy resolves and reaches the target), one `proxy_tunnel` phase for the whole CONNECT-UDP bootstrap, then `dtls_handshake` and `session`. `connection.tls` is the DTLS evidence about the target, so verification and alert findings name the target. `connection.tunnel` (kind `connect_udp`) holds the proxy leg: its resolution and addresses, the QUIC phases (`quic_handshake`, `protocol_handshake` with the SETTINGS and encoding, `request_write`, `await_response_headers`) on the same clock, the proxy's TLS, the CONNECT headers (redacted by name and value) and the proxy's status and headers. The proxy's 2xx is tunnel evidence, not a response of the target: `response` is empty. `ProtocolStatus::Udp` counts application datagrams; its `masque` facts count DTLS records per encoding.
  - Ends: the handshake deadline is the DTLS one (`dtls_handshake_timeout` when the target stays silent; the tunnel itself is fine and has no finding). A proxy reset, a lost QUIC connection or a malformed capsule stream during the handshake or session is typed in that phase with the tunnel `closed_by = abnormal` and `masque.tunnel_ended_abnormally`. A proxy FIN during the handshake fails it (`dtls_handshake_failed`); during the session it ends the session like the proxy closing a UDP tunnel (`closed_by = peer`), and nothing more is sent into it (no `close_notify`).
  - The PROXY datagram envelope stays refused with a tunnel: the proxy would relay it to the target as payload.
- **Refused before traffic.** A non-`https://` proxy URL or one with a path; a template without both variables or with other variables; an HTTP/SOCKS proxy setting; a datagram over the 65,527-byte RFC 9298 limit; a PROXY datagram envelope with a tunnel.
- **Not implemented.** CONNECT-UDP over HTTP/2 or HTTP/1.1 (there is no fallback: a UDP-blocked path to the proxy is a `quic_handshake_timeout`); several tunnels on one QUIC connection; RFC 9298 context-ID extensions. (UDP and DTLS through a mesh HBONE datagram tunnel are §3.9.)
- **Live.** `docs/lab/h3x.md`: echo, silent target, 403/400/405/501 refusals, no extended CONNECT, required QUIC datagrams and a UDP-blocked path; and DTLS inside the tunnel to a DTLS echo behind the gateway (verified handshake with ground truth from the fixture log, an untrusted DTLS certificate, a destination the route does not admit, a silent destination), against Ferrum Edge 0.9.7 and 0.9.5.

### 3.9 Mesh client: HBONE tunnels, SPIFFE server identity, SNI override

Anvil can test Ferrum Mesh (and Istio-style) mesh listeners directly, without being part of the mesh.

**HBONE proxy profile (`ProxyKind::Hbone`).** A proxy profile of kind `hbone` names the HBONE endpoint (`host:port`, for example a mesh proxy's HBONE listener or a sidecar's inbound mTLS listener) and a **TLS profile** (`tls_profile_id`, required). For each connection Anvil:

1. resolves and connects to the endpoint (`dns`, `connect`);
2. runs **mutual TLS** with ALPN `h2`, presenting the TLS profile's client identity (the client SVID) and verifying the endpoint's server identity with the same profile (normally by SPIFFE ID, see below);
3. sends the HTTP/2 connection preface, then `CONNECT` with `:authority = <request host:port>` (IPv6 bracketed). Optional headers come from the profile: a protocol marker (`x-ferrum-mesh-protocol: hbone` or `x-istio-protocol: hbone`; none by default, as Istio ztunnel sends none), a W3C `baggage` value (for example `source.principal=…`, honored by the endpoint only for trusted assertors) and extra headers. Connection-specific headers are refused before traffic;
4. treats a `2xx` as an open tunnel. The inner connection (HTTP/1.1, HTTP/2 with its own ALPN, TLS with the request's own TLS profile, raw TCP/TLS, WebSocket, SSE, gRPC) then runs over the tunnel stream exactly as over an HTTP CONNECT proxy tunnel. The endpoint resolves and dials the destination, so Anvil records the inner `dns` and `connect` phases as `not_applicable`.

Evidence keeps the two legs apart:

- The attempt's phases show the whole outer leg as one `proxy_tunnel` phase. `ConnectionObservation::tunnel` (`TunnelObservation`) holds the outer phases (`dns`, `connect`, `tls_handshake`, `protocol_handshake`, `proxy_tunnel`) on the same clock, the endpoint's addresses, the outer mTLS observation (client SVID presented, the endpoint's certificate, its SPIFFE ID and the identity check applied), the `CONNECT` headers sent, the `CONNECT` status and response headers.
- `connection.tls` stays the **inner** TLS with the destination.
- A non-2xx `CONNECT` is a typed `hbone_connect_refused` failure (phase `proxy_tunnel`) with the status and a bounded (8 KiB) body preview kept in the tunnel evidence. It is **not** a destination response: `response` is empty, dispatch is `not_dispatched`, and no HTTP-status finding is produced for the destination.
- Tunnel-leg failures are typed separately from the destination: `proxy_connect_failed` (endpoint DNS/TCP), `hbone_endpoint_tls_failed` (the mTLS handshake; the precise TLS kind and alert are in `tunnel.failure`), `hbone_protocol_error` (no `h2`, preface, stream reset, GOAWAY or the connect deadline before a `CONNECT` answer) and `hbone_connect_refused`. A TLS 1.3 client-certificate alert that arrives after Anvil's handshake is read from the mTLS stream and attributed to the TLS leg.
- Timeouts: the endpoint's DNS, TCP and TLS use the request's DNS, connect and TLS deadlines; the HTTP/2 preface and the `CONNECT` answer share the connect deadline.

A fresh HBONE connection (one HTTP/2 connection, one `CONNECT` stream) is opened per inner connection and never pooled, because the tunnel carries one execution's identity and headers. HTTP/3 through an HBONE proxy is refused before traffic (`unsupported_combination`); UDP runs as a datagram tunnel, and DTLS inside that tunnel (below). Proxy credentials are refused for HBONE (the client is authenticated by its SVID).

**UDP through an HBONE proxy (datagram tunnel).** A `udp://` request whose effective proxy is an HBONE profile runs as a Ferrum Mesh datagram-over-HBONE tunnel. The wire format is transcribed from Ferrum Edge v0.9.7; v0.9.5 has the same relay, framing and public bodies (its `src/proxy/mesh_udp_frame.rs` is identical), without v0.9.7's per-`CONNECT` credential re-admission.

- **Where it is relayed.** Only in `FERRUM_MODE=mesh` and only on inbound mesh listeners: the sidecar's mesh-mTLS inbound (`:15006`), the Ambient and node/service waypoint HBONE listener (`:15008`) and the egress gateway (`:15090`, allow-listed external UDP destinations only). Each is mutual TLS with the client X.509-SVID and ALPN `h2` (`src/modes/mesh/mod.rs:92-114, 1073-1136`, `src/tls/spiffe.rs:209-212`, `src/proxy/hbone_proxy.rs:141-160`, `src/proxy/mod.rs:31370-31374, 31455-31465`).
- **Request.** The byte-stream tunnel's outer leg, then an HTTP/2 `CONNECT` with `:authority = host:port` of the destination (IPv6 bracketed), no `:scheme`, `:path` or `:protocol`, and the protocol marker with the value `udp`: `x-ferrum-mesh-protocol: udp`, or `x-istio-protocol: udp` when the profile selects the Istio marker (Ferrum compares the value case-insensitively, and a present `x-ferrum-mesh-protocol` takes precedence over `x-istio-protocol`). The marker selects the datagram relay (`src/modes/mesh/hbone.rs:25, 242-251`); Ferrum's own mesh client sends the same request (`src/proxy/hbone_pool.rs:1843-1856, 3006-3050`, `src/proxy/mesh_mtls_pool.rs:1336-1344`). The profile's `baggage` and extra headers go on the `CONNECT` as for TCP; Anvil sends no baggage by default (Ferrum trusts `source.principal` only from configured assertors). An extra header that names a marker is refused before traffic (`local.proxy_config_invalid`).
- **Framing.** After a `2xx`, both directions carry `[u16 big-endian length][payload]` records on the stream's DATA frames: one record per datagram, at most 65,535 payload bytes, zero-length records kept, a record split across DATA frames or several records in one. `END_STREAM` ends the session, and an incomplete trailing record is dropped, never delivered (`src/proxy/mesh_udp_frame.rs`). Anvil frames and decodes with its own codec (`anvil-transport/src/hbone_udp.rs`, unit-tested over every two- and three-way split, byte-by-byte feeding, zero-length, maximum-size and truncated tails).
- **Oversize datagrams.** A scripted datagram over 65,535 bytes refuses the request before traffic (`local.request_too_large`, field `udp.datagrams[i]`). An interactive one is refused and recorded per datagram (a `not_sent` transcript entry, the channel's `oversize_refused`, `hbone.udp_datagram_too_large`), and the session goes on.
- **Evidence.** The attempt is shaped as for TCP through HBONE: DNS and connect are `not_applicable` (the endpoint resolves the destination and opens the socket), the whole outer leg is one `proxy_tunnel` phase, then `session`. `ConnectionObservation::tunnel` holds the outer leg exactly as for the byte-stream tunnel, plus `datagrams` (`HboneDatagramChannel`): records sent and received, oversize refusals, `truncated_tail_bytes`, `closed_by` and the endpoint's reset code. The transcript, counts, response window, `max_datagrams`, repeated-payload count and dispatch rules are the direct UDP adapter's; `ProtocolStatus::Udp` carries the counts. Silence is only `udp.no_response`, with the alternative that the relay gives no acknowledgement and that ICMP errors toward the destination reach the endpoint's socket (so `udp.icmp_port_unreachable` never appears through a tunnel). The connection byte counters are the outer TLS bytes after the `CONNECT`.
- **HTTP/2 driven directly.** The datagram tunnel uses `h2` rather than hyper's `CONNECT` upgrade, which reports a peer `RST_STREAM(CANCEL)` as a clean end of stream, so the evidence keeps the endpoint's `END_STREAM` apart from a reset and its code.
- **End.** Anvil ends the tunnel with `END_STREAM` when the window elapses, on Close or at `max_datagrams`, then waits up to 500 ms for the endpoint to end its side (so the close is delivered); on cancel and at the total deadline it resets the stream (`CANCEL`).
  - The endpoint's `END_STREAM` before Anvil's close is `closed_by = peer`, with no transport failure and `hbone.udp_tunnel_ended` (warning; confirmed over a verified endpoint, likely otherwise). Ferrum Edge ends its relay this way whenever the relay stops, including after an ICMP error on its UDP socket toward the destination (`relay_hbone_udp`; hyper sends `END_STREAM` for a dropped upgraded stream). Observed live: MESH-026/027.
  - A reset (`RST_STREAM`, `GOAWAY`) or a lost connection is `closed_by = abnormal` with a typed `session` failure (`h2_stream_reset` / `h2_go_away` and the code, or the I/O kind), transport `incomplete`, and `hbone.udp_tunnel_ended` (error; `unknown` when no HTTP/2 frame names who ended it). No `exchange.*` finding describes the tunnel's stream as the destination's.
  - A stream that ends inside a record is `body_incomplete` with `truncated_tail_bytes` and `hbone.udp_record_truncated`; the records before it are kept.
- **Refusals** are typed exactly as for TCP (`hbone_connect_refused`; `hbone.tunnel_refused` or, for a 5xx, `hbone.tunnel_unavailable`, quoting the public body; dispatch `not_dispatched`; nothing sent), with datagram-tunnel alternatives that are never claimed as the cause. Ferrum Edge's public answers: 403 `{"error":"HBONE UDP tunnel requires an authenticated mesh peer"}` (no authenticated peer, and in v0.9.7 also a peer that fails credential re-admission: one body for both), 403 `{"error":"HBONE UDP relay destination not allowed"}` (the effective destination after a route override, or a resolved answer outside what the terminator owns), 403 `{"error":"Mesh authorization denied"}`, 502 for an unresolved destination, a DNS failure or a local socket failure, 503 `{"error":"UDP egress relay session capacity exhausted"}`, 504 for a local socket connect timeout, 404 `{"error":"Not Found"}` (not an inbound listener, or relay synthesis refused the authority) and 405 `{"error":"CONNECT method is not allowed"}` (not mesh mode, or an unrecognized marker) (`src/proxy/hbone_proxy.rs:1480, 1528, 1597, 1678, 1726, 1862, 1919, 2148, 2162-2206`; `src/proxy/mod.rs:30940, 31526-31535`; `src/plugins/mesh/authz.rs:1266`). The mTLS refusals are the tunnel's (above).
- **Refused before traffic.** A PROXY protocol envelope through an HBONE proxy, for UDP and DTLS (mesh relays never read it); UDP through a MASQUE proxy together with an HBONE proxy; an auth profile (payloads are verbatim, as for direct UDP).
- **Live.** The `mesh` lab (`docs/lab/mesh.md`, MESH-018 to MESH-028) against Ferrum Edge 0.9.7 and 0.9.5: echo through the sidecar, silence, mTLS refusals, the UDP authenticated-peer 403, relay-synthesis 404s (sidecar and Ambient), the UDP destination 403 and DNS-failure 502 (Ambient), and the endpoint ending the tunnel mid-session.

**DTLS through an HBONE proxy (DTLS inside the datagram tunnel).** A `dtls://` request (or `udp.dtls`) whose effective proxy is an HBONE profile opens the same datagram tunnel as `udp://` and runs the DTLS client (§3.6) over it (`HboneChannel`). Every DTLS record (handshake flights, retransmissions, application data, `close_notify`) is one `[u16 length][payload]` record. Ferrum Edge's relay forwards each record as one UDP datagram on its connected socket and never looks inside (`relay_hbone_udp`, identical in v0.9.5 and v0.9.7), so the DTLS session is end to end with the target.

- **Two TLS profiles, two legs.** The proxy profile's TLS profile authenticates the HBONE endpoint (mTLS with the client SVID, the endpoint verified by SPIFFE ID); the request's TLS profile applies to the DTLS peer (trust, host-name or SPIFFE verification, and the client identity it presents, ECDSA only as for any DTLS). The same SVID may serve both.
- **Evidence.** The attempt addresses the target throughout (method `DTLS`, the `dtls://` URL): `dns` and `connect` `not_applicable`, one `proxy_tunnel` phase for the whole endpoint leg, then `dtls_handshake` and `session`. `connection.tls` is the DTLS evidence about the target; `connection.tunnel` (kind `hbone`) is the endpoint leg exactly as for UDP, and its `datagrams` channel counts DTLS records, handshake flights included (MESH-031: 6 sent and 5 received for two application datagrams and `close_notify`). `ProtocolStatus::Udp` counts application datagrams; the endpoint's 200 is tunnel evidence, never a response of the target.
- **A tunnel that never opens** (mTLS failure, a refusal, a timeout) is exactly the UDP-through-HBONE record, apart from the method and URL: the same phases, failure, tunnel evidence, `hbone.*` findings and counts; no `dtls_handshake` phase, no DTLS evidence, nothing about the target (for a refusal the two records are compared field by field in the tests).
- **Ends.** The handshake deadline is the DTLS one (`client.dtls.handshake_timeout`, with "the endpoint relays without acknowledgement" as an alternative; the tunnel itself has no finding). A DTLS verification failure or a peer alert is about the target (`client.tls.*`, `client.dtls.handshake_failed`), never the endpoint. The endpoint's `END_STREAM` during the session ends it like a peer close of a UDP tunnel (`closed_by = peer`, `hbone.udp_tunnel_ended` warning, nothing more is sent into it, no `close_notify`). An `END_STREAM`, a reset or a lost connection **during the handshake** fails the handshake typed in `dtls_handshake` and is reported as the endpoint's end (`hbone.udp_tunnel_ended`, error, "during the DTLS handshake"), never as a `client.dtls.*` or `exchange.*` finding about the target.
- **Refused before traffic**: as for UDP (a PROXY envelope, MASQUE with HBONE, auth). Load runs refuse it (`udp_hbone`).
- **Live.** The `mesh` lab (MESH-031 to MESH-034) against Ferrum Edge 0.9.7 and 0.9.5: a verified DTLS session with the workload's DTLS echo behind the sidecar (SPIFFE-verified on both legs, the client SVID presented on both; ground truth from the DTLS fixture's log: one handshake with the client SVID's CN, the application datagrams by size; the gateway's relay transaction line), a workload presenting an SVID from an untrusted root (`client.tls.untrusted_trust_domain` about the workload, the endpoint leg verified), and the relay-synthesis 404 and Ambient's UDP destination 403 with no DTLS attempted.

**SPIFFE server identity (`TlsProfile::server_spiffe`).** A TLS profile can set `expected_server_spiffe_id`, `trust_domain`, or both (the ID must then be in that trust domain; invalid values are refused before traffic). When set, the peer's X.509-SVID is verified as the SPIFFE X.509-SVID specification requires, **instead of** host-name verification:

- the chain must anchor in the profile's CA certificates (the trust bundle; server-auth EKU when present), with no DNS-name check;
- the leaf must carry **exactly one** URI SAN that is a valid `spiffe://` ID, must not be a CA, must set `digitalSignature` and neither `keyCertSign` nor `cRLSign` (a certificate with several URI SANs is invalid);
- its trust domain must equal the configured one, and with an expected ID the ID must match exactly.

Verification stays **on by default**: without `server_spiffe` the ordinary host-name verification applies. Failures are typed (`tls_spiffe_id_mismatch`, `tls_untrusted_trust_domain`, `tls_invalid_svid`; an unanchored SVID that names another trust domain is `tls_untrusted_trust_domain`) and stop the handshake before any request byte. `verify = false` still records what the SPIFFE check would have concluded. The same check applies to HTTP/1.1, HTTP/2, HTTP/3, raw TLS, WebSocket, gRPC, SSE, DTLS and the HBONE endpoint. The peer's SPIFFE ID (a single `spiffe://` URI SAN) is recorded in `TlsObservation::peer_spiffe_id` for **every** TLS server, verified or not, and `identity_check` records which check applied (`host_name`, `spiffe_id` or `spiffe_trust_domain`).

**SNI override (`TlsProfile::server_name_override`).** The configured name is sent as SNI instead of the URL host (the HTTP authority is unchanged), for example an east-west passthrough name like `outbound_.8080_._.svc.ns.svc.cluster.local` (underscores are accepted). The certificate is verified against that name, or against the SPIFFE identity when one is configured. `TlsObservation::sni` records the SNI actually sent (`None` when the name is an IP address, which TLS never sends as SNI), and `server_name_overridden` marks that it came from the profile. An invalid override is refused before traffic.

**Client SVIDs from the SPIFFE Workload API.** A TLS profile's client identity can be a PEM or PKCS#12 file, or an X.509-SVID the SPIFFE Workload API issues to Anvil (§3.11), optionally with that SVID's trust-domain bundle as the profile's trust bundle. The HBONE endpoint's mTLS and direct mesh listeners use it like any other client identity.

Live coverage: the `mesh` lab profile (`docs/lab/mesh.md`) drives the real Ferrum Edge 0.9.7 in mesh mode; the `workload` profile (`docs/lab/workload.md`) presents an X.509-SVID from Ferrum Edge's own Workload API on a mesh inbound listener.

### 3.10 PROXY protocol (TCP header, HTTP-family header, datagram envelope)

Anvil can play the load balancer in front of a listener that requires the HAProxy PROXY protocol: a stream listener such as a Ferrum Edge `tcp`, `tcp_tls`, `udp` or `dtls` proxy with `stream_proxy_protocol: true`, or an HTTP listener behind a PROXY-speaking balancer (HAProxy `accept-proxy`, nginx `listen … proxy_protocol`, Envoy's proxy-protocol listener filter, cloud load balancers). Ferrum Edge's own HTTP listeners never read a PROXY header: `stream_proxy_protocol` is rejected for HTTP-family proxies (`src/config/types.rs`, v0.9.7), which take the client address from `X-Forwarded-For` instead. The byte formats are transcribed from Ferrum Edge v0.9.7 (`src/proxy/proxy_protocol.rs`, `src/proxy/datagram_client_address.rs`); unit tests pin the gateway's own test vectors, and an HMAC tag vector computed independently.

- **TCP / TCP+TLS header** (`tcp.proxy_protocol`).
  - `version`: `v1` (text: `PROXY TCP4|TCP6|UNKNOWN …\r\n`), `v2` (binary), or `raw` (exact hex bytes, for deliberately malformed headers). Off when absent.
  - v2 `command`: `proxy` or `local` (no addresses; the receiver keeps the socket peer). `family`: `auto` (`AF_INET`, or `AF_INET6` with IPv4 promoted to its mapped form, as the gateway's encoder does) or `unspec` (v1 `UNKNOWN`, v2 `AF_UNSPEC`).
  - `source` / `destination` (`ip:port`, variables allowed) default to the connection's **real** local and remote socket addresses. Through a forward proxy those describe the proxy hop, so the request is refused before any traffic unless both are set.
  - v2 TLVs: `authority` (`PP2_TYPE_AUTHORITY`, 0x02) and any further `tlvs` (type + hex value).
  - Written after TCP connect (and after an HTTP CONNECT/SOCKS tunnel) and **before the TLS ClientHello**, in its own `proxy_protocol_header` phase whose detail summarizes the header. The connection evidence (`connection.proxy_header`) records the format, command, family, source and destination with their origin (socket or configured), the exact bytes as hex, the v1 line, TLV summaries, the length, and whether the bytes are well-formed by the gateway parser's rules (v1 up to CRLF within 109 bytes; v2 version 2, LOCAL/PROXY, address block ≤ 512 bytes). Header bytes that contain a redacted value are replaced as a whole. The transcript starts with a `proxy_protocol_header` control entry. Payload byte counts exclude the header.
  - Refused before traffic (typed `unsupported_combination` / `body_serialization`): v1 LOCAL, v1 with TLVs or mixed families, an address that is not `ip:port`, an empty raw header, a v1 line over 107 bytes, a TLV over 65,535 bytes.
- **HTTP-family header** (`proxy_protocol` on the request: HTTP/1.1, HTTP/2 over TLS and h2c, WebSocket over HTTP/1.1 and HTTP/2, gRPC and gRPC-Web, SSE). The same settings, encoder, checks and refusals as the TCP header, with these rules:
  - **Once per new TCP connection**, after connect and **before the TLS ClientHello**, in its own `proxy_protocol_header` phase, with the same `connection.proxy_header` evidence as raw TCP (no transcript entry: HTTP transcripts are messages). The source and destination default to the connection's own socket addresses.
  - **With 0-RTT early data** (§3.12): a new connection under the opt-in writes the header first, then the ClientHello that resumes a ticket and carries the request as early data; a pooled reuse writes neither again. Tested against the independent relay in front of the TLS 1.3 early-data fixture (`anvil-engine/tests/proxy_protocol_early_data.rs`, HTTP/1.1 and HTTP/2): one parsed header per connection with the configured addresses, early data accepted by the server behind it.
  - **Pooling.** The HTTP pool key includes a digest of the header plan, so a pooled HTTP/1.1 or multiplexed HTTP/2 connection is only ever reused by a request with the same plan (never by one with another header or none). A connection's header is fixed for its lifetime: a reused connection does **not** send it again, and the attempt records a `proxy_protocol_header` phase with status `reused` ("sent once when connection #N was opened") while `connection.proxy_header` still shows what that connection was opened with.
  - **The request's own listener only.** The header is configured for the request URL's `host:port`. Retries, transparent re-dispatches, DPoP challenges, SSE reconnections and redirects to the same `host:port` carry it on every new connection. A redirect to another host or port is followed **without** it: that attempt records the `proxy_protocol_header` phase as `not_applicable` ("not sent: the PROXY header is configured for A only, and this attempt goes to B") and the prepared request notes it. Anvil never assumes another origin sits behind the same balancer; send a request there directly to test it with a header. OAuth token requests never carry it.
  - **Refused before traffic** (`unsupported_combination`, field `proxy_protocol`): HTTP/3 (both HTTP/3 policies and WebSocket over HTTP/3; QUIC has no standard carriage for a PROXY header), any forward proxy (through a plain HTTP proxy the header would reach the proxy itself; through a CONNECT or SOCKS5 tunnel it would describe the proxy hop), HBONE (mesh relays never read it), and a request-level header on raw TCP or UDP, which use `tcp.proxy_protocol` and `udp.proxy_protocol`.
- **UDP / DTLS envelope** (`udp.proxy_protocol`).
  - A PROXY v2 header with the `DGRAM` transport prepended to **every** datagram (`0x21 0x12`/`0x22`, or `LOCAL` `0x20 0x00`, or `AF_UNSPEC` `0x21 0x02`). With DTLS it wraps each UDP datagram **outside** the DTLS records, handshake flights, retransmissions and `close_notify` included, because the gateway strips it before its DTLS demux. Replies are never wrapped.
  - Optional `authentication`: the shared secret (`FERRUM_DATAGRAM_PROXY_PROTOCOL_SECRET`) comes from the vault or a `{{variable}}`, is used verbatim, must be at least 32 bytes (refused before traffic otherwise; the value and its length are never reported), is added to the redactor, and is never recorded. Each datagram carries the freshness TLV `0xE1` (version 1, `sender_id`, `epoch`, `sequence`, `timestamp_ms`) and the HMAC-SHA-256 tag TLV `0xE0` over the listener's canonical identity plus the whole datagram with the 32 tag bytes elided.
  - **Listener identity the user must give**: the receive boundary (`udp`, or `dtls` when the listener terminates DTLS; the default follows the URL scheme), the listener's **bind address exactly as bound** (Ferrum: `FERRUM_STREAM_PROXY_BIND_ADDRESS`, default `0.0.0.0`; IPv4-mapped forms are folded to IPv4; a wildcard and a specific address are different identities), and the port (default: the destination port). The domain bytes are `"ferrum-datagram-proxy-v1" | 0x01 | 0x01 udp / 0x02 dtls | 0x04 + 4 bytes or 0x06 + 16 bytes | port`.
  - `epoch` defaults to Unix milliseconds at the start of the run (a fresh epoch per run); pin it with `first_sequence` to replay a sequence on purpose. `timestamp_offset_ms` shifts the timestamp to test the receiver's 30-second horizon. The sequence increases by one per datagram sent.
  - Evidence: the first datagram's envelope as hex with the tag replaced by `‹tag›`, the TLV summaries, the listener binding, sender, epoch, first and last sequence, and the number of datagrams wrapped.
- **Diagnostics.** A listener that requires PROXY protocol closes a TCP connection without data or reason, and drops a datagram silently. A listener that does not expect a header reads it as the start of the request or of the TLS handshake and rejects that. Anvil never turns any of these into a confirmed claim:
  - no header sent and the peer closed without data (`tcp.closed_without_data`, or `client.tls.connection_closed` for TLS; for HTTP-family requests on a **new** connection also `exchange.closed_before_response` / `exchange.reset_before_response`): "the listener may require a PROXY protocol header" is added as one more alternative;
  - a header sent and the peer closed without data: `tcp.proxy_header_maybe_rejected`, confidence **unknown** (untrusted source, format, or something after the header), or **likely** only when Anvil's own check found the bytes it sent malformed; for HTTP-family requests (new connections only) the close finding also gets "the listener may not expect a PROXY protocol header";
  - a header sent on a new HTTP-family connection and the listener answered **400** (`http.client_error`, `ws.handshake_rejected`, `app.grpc_status_missing`) or a **TLS alert** during the handshake (`client.tls.peer_alert` and related): "the listener may not expect a PROXY protocol header" is added as an alternative; the finding keeps its own confidence and states the public outcome only;
  - a reused connection had already been accepted by the listener, so none of these alternatives applies to it;
  - an envelope sent and nothing came back: `udp.no_response` (or `client.dtls.handshake_timeout`) with "the listener may have dropped the envelope" as an alternative. Silence stays "no response observed".
- **Not implemented.** PROXY headers over HTTP/3 or through a proxy (refused, see above), the v2 `AF_UNIX` family, computed CRC32C (0x03) or SSL (0x20) TLVs (any TLV can still be sent as type + hex), and receiving (Anvil only sends).
- **Observed limit.** A listener that answers the header on its own before the HTTP/1.1 request is written (Ferrum Edge answers the PROXY line with `400 Bad Request` and `connection: close` at once) is seen by the HTTP client as a close before any response: hyper discards a response that arrives while no request is in flight. The failure message keeps hyper's "received unexpected message from connection", and the diagnosis is the close plus the PROXY alternatives above.
- **Live verification.** The `proxyproto` lab profile runs all of this against the real gateway ([lab/proxyproto.md](lab/proxyproto.md)): the stream listeners with their PROXY settings, and (PP-HTTP-001/002) Ferrum's HTTP and HTTPS listeners, which do not expect a header. Accepted HTTP-family headers are covered against the independent `tcp_relay` receiver in front of the HTTP fixture, because no Ferrum HTTP listener accepts one.

### 3.11 SPIFFE Workload API: X.509-SVIDs and JWT-SVIDs

Anvil is a client of the SPIFFE Workload API (`SpiffeWorkloadAPI`, the standard `workload.proto` served by SPIRE agents and by Ferrum Edge's in-process Workload API). It uses what the API issues to it in two places: as a TLS client identity and as a bearer credential. `crates/anvil-transport/src/workload_api.rs` is the client; `crates/anvil-engine/src/workload.rs` uses it.

- **Endpoint.** `unix:///path/to/socket` (the SPIFFE Workload Endpoint URI; `unix:/path` too) from the profile, else the `SPIFFE_ENDPOINT_SOCKET` environment variable; the evidence records which. `npipe:<name>` is a Windows named pipe (`\\.\pipe\<name>`, SPIRE's transport on Windows). Refused before any dial, typed: `tcp://` endpoints (a TCP peer has no kernel credentials, so the server could not attest the caller), `npipe:` on Unix and `unix:` on Windows (`unsupported_combination`), a missing endpoint and a malformed URI (configuration errors).
- **Wire.** gRPC over HTTP/2 (hyper) on a fresh connection per call: `POST /SpiffeWorkloadAPI/<Method>` (the service has no proto package), `content-type: application/grpc`, `te: trailers`, the mandatory `workload.spiffe.io: true` metadata (servers reject a call without it), `grpc-timeout`, and one deadline (the request's connect timeout, 5 s when unset). The protobuf messages are transcribed from the upstream `workload.proto` with `prost`; no new dependency. For the streaming RPCs (`FetchX509SVID`, `FetchJWTBundles`) Anvil reads the first response and cancels the stream. `ValidateJWTSVID` is not called (Ferrum Edge's copy of the proto carries its claims as JSON bytes instead of `google.protobuf.Struct`); the equivalent checks run locally against `FetchJWTBundles`.
- **Typed outcomes** (`WorkloadCallResult`): connected and answered OK; unavailable (no socket at the path, permission denied, nothing listening, not HTTP/2 gRPC, cut off), with the I/O error kind; a deadline; a non-OK gRPC status with its code and the server's `grpc-message` (bounded, control characters removed, shown as untrusted text); an OK answer without an identity (no SVIDs, or none with the requested SPIFFE ID); an undecodable answer. They map to `workload_api_unavailable`, `workload_api_denied` (PERMISSION_DENIED or no identity) and `workload_api_failed`, all local preparation failures: `dispatch = not_dispatched`, nothing reaches the destination.
- **X.509-SVID client identity** (`ClientIdentity::WorkloadApi { endpoint, spiffe_id, trust_bundle }` on a TLS profile). Before a request is prepared, every TLS profile it will present an identity from — its own TLS profile for a TLS URL (`https`, `wss`, `grpcs`, `tls`, `dtls`, and a MASQUE proxy), and the TLS profile of an HTTPS or HBONE proxy — is materialized: `FetchX509SVID`, the SVID selected (the first, or the one with the configured SPIFFE ID), its chain and PKCS#8 key converted to PEM, and the profile handed to the ordinary TLS code as a PEM identity. The leaf must be a valid X.509-SVID naming the SPIFFE ID the answer states. Host bindings apply as for any identity. A plain-HTTP request never calls the Workload API.
  - **Rotation.** The fetched SVIDs are cached in memory and re-fetched once half the shortest SVID's lifetime has passed, as SPIFFE agents rotate. The prepared TLS configuration is keyed by the identity's fingerprint, so a rotated SVID never reuses the previous one.
  - **Trust.** With `trust_bundle`, the SVID's own trust-domain bundle (`X509SVID.bundle`) joins the profile's CA certificates, so a mesh server can be verified by SPIFFE ID (§3.9) with the bundle the Workload API returned. Federated bundles are recorded and never trusted: one TLS profile holds one trust bundle, and mixing trust domains' roots would let one domain's CA vouch for another's IDs.
- **JWT-SVID auth** (`AuthConfig::JwtSvid`): `Authorization: Bearer <JWT-SVID>` (header and prefix configurable). Sources: `FetchJWTSVID` for the configured audiences (and optionally one SPIFFE ID), a variable or vault value, or a file read at send time. At least one audience is required. In the desktop app the token file is chosen with **Choose…** in the native dialog, which binds it in the vault on this device; a path that was not bound that way (typed into a setting, or arriving in an import) is refused before anything is read. The CLI reads the configured path as is. Either way links are followed (a Kubernetes projected token is a rotating link), and only a regular file of at most 16 KiB is read: a FIFO or a device, reached directly or through a link, is refused, and the open never blocks.
  - **Local checks before sending**, each recorded (`JwtSvidCheck`: passed, failed, not run) with its detail: *format* (three unpadded base64url segments, JSON header and claims, bounded), *algorithm* (present; not `none`, not HMAC; one of RS/PS/ES that Anvil can verify), *subject* (`sub` is a workload SPIFFE ID, and equals the configured one when set), *audience* (every configured audience is in `aud`), *expiry* (`exp` present and in the future, `nbf` not in the future — by this machine's clock; verifiers use their own clock and leeway, for example Ferrum Edge's `jwks_auth` allows 0 s and its `ValidateJWTSVID` 60 s) and, when enabled, *signature* against the trust domain's JWT bundle from `FetchJWTBundles` (key selected by `kid`; the algorithm the key permits, never the token's word alone). The token itself is never recorded; the evidence keeps the decoded `sub`, `aud`, `alg`, `kid` and times.
  - **A failed check stops the request** (`jwt_svid_rejected_locally`, nothing sent) unless the profile explicitly sets `send_despite_failed_checks` (to see how a verifier treats a bad token). Then the checks stay on the record as warnings and the send is marked in the evidence. An import never activates that setting.
  - **Caching.** A fetched JWT-SVID is reused until half its lifetime and never within 30 s of its expiry; JWT bundles are reused for 5 minutes. Tokens and bundles live in memory only.
- **Lock.** SVIDs with their private keys, JWT-SVIDs and bundles are held in the engine's `WorkloadCache` (zeroized buffers) and cleared with the OAuth tokens and pooled connections on lock (`Engine::clear_sensitive_state`). Nothing is written to disk.
- **Findings** (catalog wording): `local.workload_api_unavailable`, `local.workload_api_denied` (with the uid this process presents in the socket's peer credentials — what the server attests), `local.workload_api_failed` (for example `UNIMPLEMENTED` from an X.509-only Workload API), all confirmed local observations; `auth.jwt_svid_expired`, `auth.jwt_svid_audience_mismatch`, `auth.jwt_svid_invalid` (errors when refused, warnings when sent anyway); `auth.jwt_svid_rejected` for a 401 after sending a JWT-SVID — confidence **unknown**, scope unknown, the public body quoted, the local checks listed as evidence and any failed check listed only as an alternative. It never claims the verifier's reason (Ferrum Edge's `jwks_auth` answers every rejected token with `{"error":"Invalid or unrecognized JWT"}`).
- **Probe.** `anvil workload probe [--endpoint …] [--audience …] [--json]` and the editors' *Test the Workload API* button ask the endpoint what it issues to Anvil (SPIFFE IDs, expiry, bundle key ids, a checked JWT-SVID) without keeping or showing a key or a token.

### 3.12 0-RTT early data (TLS 1.3 / QUIC) and `425 Too Early`

Data a client sends before its TLS 1.3 handshake completes (RFC 8446 §2.3; QUIC 0-RTT, RFC 9001 §4.6) saves a round trip on a resumed session, but it is not protected against replay: anyone who captured it can send it to the server again (RFC 8446 §8). Anvil therefore sends early data only on request, only for requests that are safe to repeat, and records exactly what the handshake did.

- **Setting.** `early_data = { enabled, extra_methods }` on any settings layer (app, workspace, folder, request, run), **off by default**. With `enabled`, GET, HEAD and OPTIONS are eligible; `extra_methods` may add the idempotent methods PUT, DELETE and TRACE (RFC 9110 §9.2.2), and only by explicit choice. A policy that lists any other method (POST, PATCH, CONNECT, anything custom) is refused before traffic (`unsupported_combination`, field `settings.early_data.extra_methods`). A request whose method is not eligible is **sent after the handshake**, with `not_used = method_not_eligible` in its evidence; it never fails because of the opt-in and is never sent early. The desktop editor offers the toggle and the three idempotent methods; the CLI has `anvil send --early-data [--early-data-method PUT …]`. Import turns the opt-in off with a warning (like the other replay-relevant opt-ins), and load plans that enable it are refused (§1).
- **Session tickets.** Early data needs a ticket from an earlier connection. Under the opt-in, connections go through a session-ticket cache kept **in memory only** (never persisted, exported or shared) and cleared on vault lock and workspace deletion together with pooled connections and OAuth tokens. A ticket belongs to exactly one workspace isolation, transport (QUIC or TCP), host and port, TLS profile (by id and revision, plus a fingerprint of its trust anchors, verification, SPIFFE identity, SNI override, minimum version and client certificate chain) and ALPN list; it is never offered anywhere else. rustls resumes a ticket only with the verifier and client-certificate resolver instances that obtained it, so each cache context keeps one of each; their evidence is routed to the connection holding the context's handshake gate, which serializes handshakes *of one context* (the wait is the attempt's `queue` phase). A single `anvil send` process therefore starts without a ticket; `anvil run` and the desktop app keep tickets across requests until the lock. Outside the opt-in nothing changes: every connection is a full handshake.
- **Connection reuse comes first.** 0-RTT is a property of a *new* connection. With connection reuse on, an established pooled connection carries the request (`not_used = connection_reused`); turn reuse off to exercise 0-RTT.
- **HTTP/3 (QUIC 0-RTT).** When the resumed ticket allows early data, quinn's `Connecting::into_0rtt` returns the connection before the handshake completes; HTTP/3 is set up on it and the request is written as 0-RTT data. The handshake is then observed (`ZeroRttAccepted`):
  - accepted: the response is read as usual;
  - **rejected**: the server discarded the early data unread (RFC 9001 §4.6.2), so Anvil sets HTTP/3 up again on the now established connection and writes the same request once more, in the same attempt. This is how QUIC delivers rejected early data, not an application retry; the evidence says `resent_after_handshake` and the second `request_write` phase says why. A request stream that was opened after the handshake completed is live and is never written twice (quinn's typed `ZeroRttRejected` tells the two apart);
  - the handshake fails after the request was written: dispatch `may_have_been_sent`, because the server may have acted on the early data.
  Early bytes are counted until the moment quinn reports the handshake complete: the request's logical size (estimated QPACK header size plus body bytes), marked estimated. When the handshake wins the race against HTTP/3 setup (seen on loopback with a debug build), the request goes out as ordinary data and the evidence says `handshake_completed_first`; it is never claimed as early data. A server that answers early (for example `425`) and stops reading the request no longer turns into a write failure: the response is read.
- **TLS 1.3 over TCP (HTTP/1.1, HTTP/2).** tokio-rustls hands the stream over before the handshake completes; writes go into early data behind the ClientHello and the first flush completes the handshake. Early data is written before the protocol is negotiated, so it needs a single offered ALPN: the HTTP/1.1-only or HTTP/2-only policy (with Auto the connection resumes without early data, `not_used = alpn_not_fixed`). The hyper connection task starts only after the request is queued, so the request itself (the HTTP/2 HEADERS, not just the preface) is what travels early. Early bytes are exact TLS plaintext bytes. A rejected early copy is written again by tokio-rustls after the handshake (`resent_after_handshake`). The `tls_handshake` phase ends when the handshake actually completed, which overlaps the request write. Through a forward proxy or tunnel no early data is sent (`not_used = through_proxy`).
- **Resumed sessions in the TLS evidence.** No certificate is exchanged on resumption: `resumed = true`, the chain shown is the one stored with the ticket, and verification is the original handshake's (a verifying profile only ever holds tickets from handshakes its verifier passed; with a bypass the stored chain is checked again to say what strict verification would conclude). `client_certificate_requested` is not observed.
- **`425 Too Early` (RFC 8470 §5.2).** The status says the server declined to process a request that might be replayed. For a request **eligible under the opt-in** (and an `https` URL), Anvil sends it **once** more after the handshake completed, never as early data: attempt reason `too_early_retry`, on the connection that answered 425 (kept for that retry even with reuse off), else on a new one without early data. Never more than one retry; a second 425 is the final answer. Without the opt-in, or for an ineligible method, a 425 is reported and not retried.
- **Evidence** (`AttemptObservation.early_data`, present only under the opt-in): transport; whether the method was eligible; resumption offered and accepted; early data offered and accepted/rejected; bytes; `resent_after_handshake`; `not_used` (`no_ticket`, `ticket_without_early_data`, `method_not_eligible`, `connection_reused`, `retry_after_too_early`, `alpn_not_fixed`, `through_proxy`, `handshake_completed_first`); tickets that arrived during the attempt and the newest one's `max_early_data_size`. The desktop Connection tab shows it per attempt, the Timing tab the early bytes and the overlapping phases, the Attempts tab the per-attempt outcome and the 425 retry.
- **Findings** (`protocol.early_data`, wording in the findings catalog): `early_data.accepted` (info, confirmed, `client_to_peer`, with the replay note in "does not prove"), `early_data.rejected` (info: the re-send is the protocol, not a retry; the reasons a server rejects stay alternatives), `early_data.no_ticket` (info: a full handshake that delivered no ticket), `early_data.ticket_without_early_data` (info: resumption only), and `request.too_early` (confirmed that the server declined to process; scope unknown, because a gateway's early-data policy and a backend that saw `Early-Data: 1` look the same; names the retry outcome; for a request not sent as early data it says so and lists the alternatives, including an `Early-Data: 1` request header and servers that count requests racing the handshake as early). Anvil never sends `Early-Data` itself (that header is for intermediaries, RFC 8470 §5.1).
- **Ferrum Edge** (v0.9.7 `8fed134`, whose line numbers are cited; the early-data code is identical in v0.9.5 `20e7603` apart from log formatting; live in [lab/early.md](lab/early.md)):
  - only the **HTTP/3 listener** accepts early data, and only when `FERRUM_TLS_EARLY_DATA_METHODS` is set on a listener without frontend mTLS (`src/http3/peer_identity.rs` `zero_rtt_admitted`, `quic_max_early_data_size`). Its QUIC TLS config then uses `max_early_data_size = u32::MAX` and a stateful session cache bounded by `FERRUM_TLS_SESSION_CACHE_SIZE` (default 4096) instead of the stateless ticketer (`src/http3/server.rs` `build_h3_quinn_server_config`, lines 700–745). rustls issues 2 tickets per handshake with a 24-hour lifetime, takes a stateful ticket out of the cache on use (single use: a replayed ClientHello finds nothing) and accepts early data only within a 60-second ticket-age window and with the same version, cipher suite and ALPN (rustls 0.23 `server/tls13.rs`);
  - the **HTTPS (TCP) listener never accepts early data** in either release: `tls::enable_early_data` only logs that it is ignoring the setting because per-request early-data state is unavailable on tokio-rustls (`src/tls/mod.rs` 2178–2195), and `max_early_data_size` stays 0 (line 1547). Its stateless tickets resume sessions without early data;
  - a request stream accepted while the QUIC handshake is still in progress is early data (the 0.5-RTT accept path, `src/http3/server.rs` 1731–1790; accept polling is biased ahead of the handshake-completion signal, 1973–1979). A method outside the list gets `425 {"error":"Method not allowed in 0-RTT early data"}` before routing (lines 2805–2825; gRPC gets `grpc-status 14`); CONNECT-UDP in early data always gets 425 (2720–2741). An admitted request reaches the backend with `Early-Data: 1`, any client-supplied `Early-Data` removed (`src/http3/cross_protocol.rs` 1136–1178, 5389–5440; WebSocket bridge `src/http3/websocket.rs` 277–305);
  - on the HTTPS path a request that *carries* `Early-Data: 1` with a method outside the list also gets that 425 (`src/proxy/mod.rs` 30953–30988). The release catalogs' outcome `gateway.admission.early_data_rejected` now cites both paths.
- **Not implemented.** Early data for sessions (WebSocket, gRPC, SSE, TCP, UDP) and through proxies or tunnels; early data with more than one offered ALPN over TCP; persistent tickets (by design); load runs with early data (refused).

## 5. Honest limitations summary

1. **WebSocket over HTTP/3 (RFC 9220)** depends on a vendored `h3` 0.0.8 carrying one upstream commit until an `h3` release includes it. Each session opens its own QUIC connection; there is no pooling across sessions. gRPC over HTTP/3 uses the same vendored `h3` (no extended CONNECT is needed there).
2. **WebSocket permessage-deflate** runs on a vendored tungstenite 0.30.0 with an Anvil-written codec patch until a tungstenite release has one (`vendor/README.md`). Anvil sends one offer (no alternative offers), compresses at the default level, sends its messages uncompressed when the server allows only a 2^8 window (zlib cannot compress that small), and does not check that a server stays within a smaller window it agreed to. The totals are per session, not per message. No other WebSocket extension is supported.
3. **Load generation.** `anvil-load` has a load unit for every protocol here except client-streaming and bidirectional gRPC and UDP or DTLS through a MASQUE or HBONE tunnel, which are refused before traffic, as are gRPC with server reflection, SSE with reconnection and mixed-protocol plans (see `docs/load.md`). There is no load action that holds sessions open while sending messages at a rate; a WebSocket unit is connect → script → close, and its round trips assume echo-style replies.
4. **DTLS.** dimpl validates only the leaf and sends only the leaf. It is ECDSA-only, and it presents an ephemeral certificate when an identity is requested but none is configured. It does not expose the cipher suite. CertificateRequest cannot be observed for DTLS 1.3. DTLS runs over a direct UDP socket, a CONNECT-UDP tunnel or an HBONE datagram tunnel.
5. **gRPC.** No outbound compression, and no retry or service-config semantics. Proto imports resolve by attachment file name only. A manually sent call opens its own connection (including a fresh QUIC connection over HTTP/3); only the load engine's persistent mode reuses pooled channels. gRPC-Web is limited by the protocol to unary and server streaming, cannot use server reflection, sends no request trailer frame, and supports protobuf messages only.
6. **SSE.** No reconnect after a clean end of stream, which differs from browser behavior. Compressed streams are not supported. Over HTTP/3 each attempt opens its own QUIC connection (no pooling).
7. **UDP.** Connected-socket mode only. Replies from a different address or port are not accepted.
8. **Connections.** Session adapters open a fresh connection per execution or session. Unlike HTTP/1.1, HTTP/2 and HTTP/3, they do not use the pool — except gRPC calls in a load run's persistent mode, which reuse a per-virtual-user channel.
9. **HBONE.** One tunnel per inner connection or UDP session (no HTTP/2 stream sharing across executions). No double-HBONE (tunnel inside a tunnel), no HBONE over HTTP/3 (QUIC), and no Anvil-side capture: Anvil is a direct client of the endpoint. A `CONNECT` refusal is reported with its public status and body only; which mesh policy refused is never claimed. UDP through HBONE uses the Ferrum Mesh datagram framing (`[u16 length][payload]` records behind the `udp` marker), which is Ferrum's, not an Istio standard (DTLS runs inside it, record for record); ICMP errors toward the destination are seen by the endpoint only, and the reason an endpoint ends a tunnel is never sent, so it is never claimed.
10. **SPIFFE.** One trust bundle per TLS profile (its CA certificates, optionally the Workload API SVID's own trust-domain bundle); federated bundles from the Workload API are recorded, never trusted; no SPIFFE federation bundle endpoint and no revocation checking (as for every TLS profile). The Workload API client reads only the first response of its streams (a later execution re-fetches instead of listening for pushes), does not call `ValidateJWTSVID` (the same checks run locally against `FetchJWTBundles`), refuses `tcp://` endpoints, and treats a 401 after a JWT-SVID generically (a 403 gets only the ordinary status findings). Windows named-pipe endpoints are implemented and tested only by the Windows CI job; the live lab covers Unix sockets (macOS, Linux). SPIRE itself is not in the lab: its Workload API is the same standard service, exercised here through the independent fixture and Ferrum Edge's server.
11. **CONNECT-UDP (MASQUE).** HTTP/3 only, one tunnel per QUIC connection, and Context ID 0 only. DTLS inside the tunnel is supported; a PROXY datagram envelope inside it is refused.
12. **PROXY protocol.** Sending only: on TCP/TLS sessions, on HTTP-family requests over TCP (once per new connection, pooled per header plan, only to the request's own `host:port`; not over HTTP/3 or through any proxy), and as the datagram envelope on UDP/DTLS. The authenticated envelope follows Ferrum Edge's (application-reserved) TLVs 0xE0/0xE1; other receivers need the same definition.
13. **0-RTT early data.** HTTP requests only (no sessions), direct connections only (no proxy or tunnel), one offered ALPN over TCP (HTTP/1.1-only or HTTP/2-only), a new connection (reuse wins when a pooled connection exists), and tickets in memory only (a single `anvil send` process never has one). Handshakes that share a ticket context are serialized. HTTP/3 early bytes are the request's logical size with an estimated header size, not QUIC packet bytes, and they count up to the moment Anvil sees the handshake complete. Load runs refuse early data. Against Ferrum Edge only the HTTP/3 listener accepts early data; its HTTPS listener resumes sessions without it.
14. **Diagnostic wording.** Three findings (`grpc.reflection_unavailable`, `udp.icmp_port_unreachable`, `udp.repeated_payloads`) carry their wording inline in the engine, not in `catalog/diagnostics/findings.en.json`. They should move into the catalog once the catalog owners agree.
