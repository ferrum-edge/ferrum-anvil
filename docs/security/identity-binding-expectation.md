# Draft: authenticated identity binding expectation

Status: opt-in partial remediation candidate for [GHSA-32jf-w2pr-fvvp](https://github.com/ferrum-edge/ferrum-anvil/security/advisories/GHSA-32jf-w2pr-fvvp), originally based on main `4254ea84c101bdc9231a4c6f455421e22468d0ec` and now normally integrated with main `07f7182b3aa6c244140b7ec3edab5a1668318c96`. No released binary, patched range, real provider ceremony, platform durability acceptance, or whole-profile freshness fix is claimed. The historical root review and hosted evidence below apply to their exact recorded heads; the current main-integrated candidate requires fresh qualification. Format and caller adoption remain an explicit owner decision. This proposal stays opt-in and draft pending that decision and packaged physical acceptance.

## Guarantee and entry points

The opt-in `anvil-profile-identity-v1` header has a mandatory `identity_binding` expectation and mandatory DEK-derived protection MAC. The existing MAC input is extended with the format and the entire serialized expectation, including the journal. A stable expectation records either explicit absence (never linked or explicitly unlinked), or binding version 1 and SHA-256 of the exact `identity.json` bytes. The sealed binding still authenticates provider, subject, policy and timestamp under profile-specific AEAD associated data.

`ProfileManager::unlock` and its fresh-login variant check that expectation, unwrap and authenticate the header, and verify a present binding before returning a key for profile installation. Missing, truncated, malformed, different-profile, old, wrong-version or changed binding files refuse ordinary unlock when required. Unexpected binding files also refuse an explicitly unlinked draft profile. An attacker cannot turn a required expectation into absence, remove it, remove the MAC, or weaken the journal while retaining a valid new-format header. Lock-screen hints remain unauthenticated UI information until the data key verifies the MAC; hints never authorize installation or reconstruction.

New passphrase and recovery wraps use distinct AEAD labels. Previously created experimental keychain profiles use a distinct credential-store tag that requires the draft header format; their existing unlock/conversion support remains. New draft keychain enrollment is now refused. Stripping the expectation/MAC and changing the plaintext format to legacy therefore cannot unlock these new wraps or entries. Passphrase rewrap and keychain conversion retain the format/expectation. An opened draft `App` refuses a disk-header format change before resealing it; credential rewrites check format again under the header lock. This is format downgrade resistance for newly created draft profiles, not freshness of historical authenticated snapshots.

The normal CLI/desktop creation paths remain legacy. Passphrase evaluation is explicitly opt-in through `ProfileManager::create_passphrase_with_identity_expectation` or `create_passphrase_profile_with_identity_expectation`; both create a real recovery wrap. `create_keychain_profile_with_identity_expectation` returns `DraftKeychainEnrollmentDeferred` before creating directories, files or OS-store entries. No ordinary required-binding check is weakened. Keychain enrollment must remain deferred until the owner approves a separate explicit repair ceremony for a deleted finalized binding; this proposal invents no such ceremony. Standard legacy keychain creation/unlock remains supported. Desktop and CLI installation consumers use the checked interface below. No contracts, database schema or release default are changed. Legacy link/unlink mutations are refused with `LegacyEnrollmentRequired`; built-in providers are already unregistered and refuse authentication. There is no new human-provider implementation. The existing test-only mock provider performs the fixture loopback PKCE ceremony; its proof is synthetic test evidence, not human credential acceptance.

## Ordered publication and recovery

The write-ahead journal is embedded in the authenticated header, so it cannot be lost independently of that header. It stores the next binding digest/version and the exact next binding file (sealed data plus public hint), or authenticated absence for unlink. It contains no plaintext e-mail, token, recovery key or DEK. There is no claim of a transaction atomic across files.

Under the required profile header lock, link/relink/unlink authenticate the current header and local credential and apply the current identity policy before publication:

1. Write and sync a unique exclusively created header temporary, rename it over the header, then strictly sync the profile directory. The header now records the pending journal while retaining the previous stable expectation.
2. Write/sync a unique binding temporary, rename it over `identity.json`, and strictly sync the directory; for unlink remove the binding entry and strictly sync the directory.
3. Publish and strictly sync a final MAC-protected header with the next stable expectation and no pending journal.

Before step 1 the previous complete state remains authoritative. At every interruption after pending publication and before final publication, ordinary unlock refuses `PublicationPending`, even if the binding is absent or already contains the next bytes. A crash before a rename leaves the earlier complete header. A failed durability barrier returns an error and never advances to the next step; the caller must reread rather than assume failure means no publication. A final-header rename that succeeds before an error may already have completed the operation. Stale temporary files are not recovery authority. Required locks also serialize credential rewrites; unsupported locking refuses these operations rather than proceeding without serialization.

`ProfileManager::recover_identity_publication` is a separate explicit API that re-enters a valid local unlock credential, authenticates the pending header/journal, verifies a journal binding under the DEK, and resumes its already authorized intent. It does not require the old provider proof again: the journal itself records the previously authorized mutation. It can repeat a binding write/removal while pending; once finalized it refuses because no journal remains. It never uses an attacker plaintext hint or missing on-disk binding to reenroll. Credential changes and a second identity publication refuse while pending. Ordinary unlock does not invoke this API.

After the recovery key authenticates the header, recovery-key unlock, explicit link and explicit unlink skip all binding metadata/open/read/parse operations. A FIFO, device, symlink/reparse point or oversized binding cannot block credential verification, and a wrong key cannot publish or remove anything. Recovery unlock intentionally bypasses provider policy and bad/missing binding data, and may open the profile without repairing identity state. It still requires the correct data key and an authentic supported header; a changed MAC, expectation or format is not bypassed. After explicit recovery unlock, explicit unlink/relink can establish a new state. A pending publication must first be explicitly resumed. Historical experimental keychain profiles have no offline recovery wrap; only an authenticated pending publication can be resumed with their valid local keychain credential. A deleted binding after final publication has no approved repair path, which is why new enrollment is refused. Ordinary unlock/link/unlink of those profiles continues refusing a missing required binding. No unavailable keychain fallback is added.

Durability is conditional on the filesystem honoring exclusive creation, advisory locks, atomic same-directory replacement, file sync and directory sync. This draft reuses the existing vault temporary-write and directory-sync primitives, with strict barriers for joint publication. Rename replaces a destination symlink rather than following it. This does **not** establish held-directory confinement against an active attacker swapping ancestor paths or lock-file entries during operations. Root must coordinate with the filesystem owner if that stronger boundary is required; no path-based file-grant helper is used and no filesystem-owner files are edited. Windows directory-sync support, filesystem-specific failure behavior and actual power-loss acceptance still need hosted/platform qualification; unsupported sync must remain fail closed. Do not weaken strict sync to best effort to make a platform test pass.

Ordinary binding reads have a 64 KiB cap (including the sealed hex envelope) before JSON parsing. They require a regular file, open with Unix `O_NONBLOCK | O_NOCTTY | O_NOFOLLOW` or Windows `FILE_FLAG_OPEN_REPARSE_POINT`, and reject reparse attributes and non-disk handles. Windows denies write/delete sharing while the descriptor is held. The descriptor survives the bounded read, exact-byte digest check and sealed-identity verification; descriptor/path identity and file metadata are checked again during verification. Unix checks device/inode and Windows uses the already locked `winapi-util` public handle-information API. No unmerged grant/capability code or dependencies are used. Limits also apply to newly generated binding contents and recovered journal parsing.

`ProfileManager::authorize_unlock(dir, how, proof)` returns a single-use `UnlockAuthorization` with private authenticated header, key, recovery authorization and optional actual provider proof. It holds no mutex or file descriptor between authorization and installation. `install` reacquires the profile lock, authenticates the current header, requires the exact checked header snapshot, reopens/verifies the current bounded binding for ordinary authorization, rechecks proof freshness, and holds the profile lock and binding descriptor through its synchronous callback. Recovery authorization again skips the binding. `open` runs `App::open` inside that callback. The callback must not await, nest a header writer, retain the raw key for later installation or perform unrelated work. Advisory-lock contention on the repository-owned `profile.lock` entry uses a five-second bounded retry; contention refuses rather than waiting indefinitely. Different profiles have independent locks. Repository writers never replace the lock entry, but this is not a lease against an external user replacing it.

Desktop `profile_unlock` and `profile_create` route both newly opened and already published Apps through `DesktopState::install_authorized`; its existing store/desktop epoch fence still gives a concurrent lock or profile switch priority. CLI `open_app` uses `UnlockAuthorization::open`. `cmd_identity.rs` exposes the provider catalogue and target-API sign-in, with no application-profile provider-unlock/install path to migrate. Actual mock-provider integration tests pass their `VerifiedIdentity` into authorization. The desktop E2E startup helper at `apps/desktop/src-tauri/src/lib.rs` also uses `authorize_unlock` and `install_authorized`. That integration was queued after the overlapping #312 writer exited and qualified through the real native startup on all three hosted operating systems. No built-in provider is enabled.

The historical tuple unlock APIs remain source compatible for existing trusted callers, but do not carry an installation fence. Lazy legacy MAC/tag upgrades and retired-entry cleanup remain; their returned maintenance headers are never substituted into authority. If maintenance ran, credential and binding verification reread the actual header under the lock before returning the updated snapshot. Direct `App::open`, `App::unlock` and `App::unlock_if` still accept a caller-held DEK as low-level trusted APIs. New installation consumers must use the authorization interface. Adoption/deprecation of this additive public interface, migration of external callers, format adoption and legacy enrollment remain explicit owner decisions pending qualification. External exhaustive `VaultError` matches must account for the new `DraftKeychainEnrollmentDeferred` variant; source migration/approval for those consumers is pending. The proposal does not silently enroll legacy profiles or claim that arbitrary raw-key consumers enforce provider policy.

These fences serialize cooperating Anvil writers. They do not hold directory handles or establish ancestor confinement, resist external lock-file replacement, revoke an already installed session when a later policy change completes, or prevent an external user/mount attacker changing files between the last check and installation. The existing path-based header read also remains outside the bounded binding reader. Stable cross-process lock ownership under hostile replacement, header/ancestor confinement, filesystem-specific failures, real power loss and packaged human acceptance remain root/owner qualification gates. No root/external-user atomic lease is claimed.

## Migration, release and rollback decision

Legacy headers remain readable with their historical behavior. A missing legacy identity file cannot distinguish never linked from attacker deletion. This candidate deliberately does not automatically migrate, reenroll or certify legacy state. Its repair guarantee starts with explicit creation of a new draft-format profile. Legacy bindings still undergo sealed verification when present, and recovery-key unlock remains available. Existing backup import/restore and database checkpoint restore do not carry the local binding/header; they cannot establish the missing historical expectation. No backup, checkpoint or database code changes are included.

Owner format question, to be taken up only after root qualification: should this separate incompatible header/wrap format become a release default, and what explicit legacy enrollment, recovery and downgrade policy should accompany it? An in-place migration must verify current credentials and any present binding, disclose ambiguity when legacy identity is missing, and replace **all** unlock paths with downgrade-resistant wraps/tags before claiming the new guarantee. Rewrapping only the entered passphrase while leaving a legacy recovery wrap is insufficient. The current prototype does not offer that migration or its native consent UI.

Proposed rollout: retain this draft/opt-in status; qualify the exact commit; obtain the owner format/migration decision; implement any approved caller/migration work under assigned ownership; then publish a version-specific guarantee with signed packaged acceptance. Do not silently make `create_passphrase` or `create_keychain` adopt the new format in main.

Rollback plan: keep legacy data untouched and keep the candidate binary available to unlock candidate profiles. Older binaries cannot open the candidate wraps or historical experimental keychain tag and must not be offered as a transparent downgrade. Recover publication with the candidate first, then deliberately export an encrypted portable backup and restore into an explicitly chosen legacy/new profile if the owner approves losing the new guarantee. Do not remove expectation/MAC fields, rewrite format strings, reuse candidate keychain entries as legacy keys, or automatically restore an old full profile as a downgrade repair. Existing backup formats require no modification for this plan, but the owner must approve the release/recovery UX separately.

## Whole-profile rollback remains unresolved

A retained authentic old header with its matching binding (including old absence), encrypted database and usable unlock credential remains an authentic old complete state. The unchanged DEK also means old authentic passphrase wraps still work when their complete old header is restored. The hosted regression explicitly records acceptance of a consistent old snapshot as an unresolved limit, while isolated binding deletion/replacement refuses.

Replayable counters, signatures, digests, journals, DEK rotation and ordinary OS credential-store entries cannot distinguish that complete valid historical state from when it was current. DEK rotation can protect current ciphertext from an old wrap; it cannot make a retained old header/key/database unreadable. This candidate does not add an OS anchor or claim hardware monotonicity. The advisory therefore remains open beyond this partial repair.

Exact unblock for whole freshness: the owner selects an authority outside the agreed attacker restore boundary (an independently protected OS-store anchor only for a threat model excluding its restore/modification, or an online authority/evidenced platform mechanism for a stronger boundary). Specify enrollment, missing/unavailable authority behavior, concurrency, authenticated header/identity/database generations and deletion coverage, and explicit authorized backup/checkpoint restore as a new generation. Missing authority must not silently reenroll existing state. Root then schedules storage integration after its existing owner and obtains physical acceptance on signed packaged builds for every supported OS. No native-consent or network-use advisory is addressed here.
